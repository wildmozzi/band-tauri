# 네이티브 엔진 구현 메모

`native-engine-design.md` 1~4·7절 구현(브랜치 `wildmozzi/ovh-engine`)에 대한 메모. 설계와 달라진 점, 미검증 부분, 측정 결과를 적는다.
엔진 리뷰(H1~H3, M1~M12, L1~L12) 반영 내역은 아래 "리뷰 반영" 절에 있다.

## 빌드 방법

- 기본 빌드: `cargo build` (WASAPI만). ASIO는 `cargo build --features asio` (`CPAL_ASIO_DIR`에 ASIO SDK 필요).
- `client/src-tauri/.cargo/config.toml`에 `CMAKE_POLICY_VERSION_MINIMUM=3.5`를 넣었다. CMake 4.x가 libopus(audiopus_sys)의 오래된 `cmake_minimum_required`를 거부하기 때문이다.
- `tauri::generate_context!`는 `client/dist`가 있어야 컴파일된다. 프론트를 빌드하지 않은 환경에서는 빈 `client/dist/index.html`이 필요하다(dist는 gitignore 대상).
- Windows 스마트 앱 컨트롤이 켜져 있으면 cargo 빌드 스크립트 실행이 차단된다(os error 4551).

## 파일 배치

설계 1절과 같다. 추가한 파일은 다음과 같다.

- `engine/worker.rs` — 워커 루프, 장치 클럭 추정(`DeviceClock`), 로컬 입력 FIFO(`LocalFifo`).
- `engine/prio.rs` — 워커/수신 스레드 MMCSS 등록과 FTZ/DAZ.
- `manager.rs` — 엔진 수명 관리(시작/정지를 락 밖에서, 세대 번호로 취소 처리). `commands.rs`는 이것의 얇은 async 래퍼다.
- `engine/device.rs`의 `fake` 모듈 — 테스트용 가짜 오디오 장치(`FakeBackend`). 통합 테스트에서 써야 하므로 `cfg(test)`가 아니라 공개 모듈이다.

오디오 I/O는 `AudioBackend` 트레이트로 추상화했다(`CpalBackend`와 `FakeBackend`). `cpal::Stream`은 `Send`가 아니어서 `open`은 엔진 전용 오디오 스레드에서 호출되고, 스트림 가드도 그 스레드에서 drop된다.

## 설계 대비 달라진 점 / 해석한 부분

계약(패킷 키 의미, `EngineStats` 필드, `estLatencyMs` 정의, 지터 버퍼 측정 규칙)이 바뀐 부분은 설계 문서도 함께 갱신했다.

| 항목 | 설계 | 구현 | 이유 |
|---|---|---|---|
| 워커 대기 | `park_timeout(≤1ms)` | `thread::sleep(500µs)` | RT 콜백에서 `unpark`(시스템콜)를 부를 수 없으므로 어차피 폴링이다. Windows에서 std `sleep`은 고해상도 타이머를 쓰고 `park_timeout`은 15.6ms 해상도일 수 있다. |
| 출력 링 수위 | 장치 버퍼 + 프레임 | 장치 버퍼 + 64샘플 청크 + 적응 여유(xrun마다 청크씩, 최대 장치 버퍼 1개, 10초 무사고 시 감소) | 출력 생산을 네트워크 프레임과 분리해 프레임만큼의 불필요한 지연을 없앴다(M1). **P1-0에서 믹스된 출력 링 자체를 없앴다**(아래 "P1-0" 절). 이 수위 규칙은 로컬(모니터) 소스 링에만 남았다. |
| keepalive / RTT | keepalive 1초 + RTT 500ms | 500ms Ping 하나가 둘 다 겸함 | 패킷 수 절감. 5초 무응답이면 Reconnecting, 15초면 Failed(설계 그대로). |
| 지터 버퍼 깊이 측정 | 정의 없음 | `now − ts(재생 위치) − min_transit`. **출력 버스트 종료 시 1회, 출력 콜백 시각 추정치(장치 클럭)로** 측정 | 워커 기상 지연이 깊이에 섞이면 제어가 발산한다(CI 실패 원인, 아래). |
| 목표 깊이 | `ceil(p95/F)+1` 프레임 | 그대로. 양자화에 ±F/4 히스테리시스, 내릴 때 2초 유지 | p95가 프레임 경계 근처면 목표가 25↔30ms로 떨려 불필요한 보정이 생겼다. |
| 샘플 보정 | 명시 없음 | 데드밴드 + 히스테리시스(진입 ±max(F/2, 1ms), 해제 ±max(F/8, 4샘플)), 모드가 켜져 있을 때만 패킷당 1샘플, 프레임 전체 램프 | 드리프트 0에서 보정 0회(M2). 국소 피치 편차는 1/F(240샘플이면 약 7센트). |
| 패킷 단위 버림 | 3프레임 이상이면 버림 | 추정 깊이와 **실제 쌓인 양**이 모두 목표를 3F 넘으면 시작, 1F 안으로 들어오면 멈춤. 버린 패킷도 디코드하고 다음 프레임과 48샘플 크로스페이드 | 추정이 틀려도 실제 데이터가 없으면 버리지 않는다(M3). |
| 재생 시작 | 명시 없음 | 시작 시 깊이를 목표에 정확히 맞춘다(초과 패킷/샘플은 건너뜀) | 시작 직후 보정이 필요 없다. |
| 언더런(다음 패킷과 그 뒤가 모두 없음) | 명시 없음 | 은닉 프레임을 끼우되 seq는 전진하지 않는다(늦게 온 패킷을 재생해 깊이를 늘림). 200ms 지속되면 재버퍼링. | 지터 급증에 자동으로 적응한다. 뒤 패킷이 이미 있으면 손실로 보고 seq를 전진한다. |
| PLC 은닉 프레임 | Opus PLC/FEC, PCM 페이드 | 그대로 | `RestrictedLowdelay`는 CELT 전용이라 Opus in-band FEC(SILK 전용)가 실제로는 동작하지 않는다(L2). `set_inband_fec(true)`는 호출하지만 손실 복원은 사실상 PLC다. 필요하면 저비트레이트 중복 전송을 따로 설계해야 한다. |
| 패킷 암호화 키 | 송신자 키 1개를 모든 수신자가 공유 | **피어 쌍별 키**: descriptor `key` = X25519 공개키, 방향별 키 = HKDF-SHA256 | 공유 키면 방 안의 누구나 다른 연주자를 사칭할 수 있었다(M7). |
| ssrc 충돌 | 같은 ssrc면 교체 | 같은 peerId만 교체. ssrc가 겹쳐도 수신 시 복호화에 성공하는 피어로 판정 | 다른 사람의 ssrc로 descriptor를 보내 피어를 지우는 공격 차단(M7). |
| 후보 | 제한 없음 | 최대 8개. 0.0.0.0·멀티캐스트·브로드캐스트·포트 0·IPv6·루프백(테스트 옵션 제외) 거부 | Hello 반사 폭주 방지(M8). |
| 경로 규칙 | Hello/HelloAck 출발 주소를 경로로 | 확정 경로가 아닌 주소의 Hello는 상태/생존 시각을 갱신하지 않음. 같은 주소에서 5회 연속이면 리바인딩으로 보고 전환. 리바인딩 후보 주소도 Hello 대상에 포함 | M6. |
| 재전송 방어 | 없음 | 제어 패킷은 타입별로 이전보다 큰 seq만 받음. HelloAck는 피어당 50ms에 1회. 버퍼링 중 seq 되감기는 목표 깊이 이내로 제한 | L5, L6. |
| STUN | 2개 서버 | 동시에 질의(전체 1.5초 상한), 응답 출발지 = 서버 주소 확인 | 오프라인 시작 지연 3초 → 1.5초(L7). 25초 주기 갱신은 아직 없음. |
| 모니터 / 믹스 탭 | — | 로컬 입력은 `LocalFifo`를 거친다(아래 H1/M5). 믹스 탭 = 피어(gain·pan·mute) + 내 입력(단위 게인), master/monitor 설정 무관, soft clip | 탭은 관람자 송출용이라 내 모니터 설정과 분리했다. |
| `engine_test_start` | 모니터만 | 시작 시 `monitor_enabled=true`, 테스트 종료(또는 실제 세션 시작) 시 원래 값으로 복원 | L4. |
| 커맨드 실행 | 명시 없음 | 모든 커맨드 `async`. 시작/정지(STUN, 장치 열기, join)는 엔진 락 밖에서. 시작 중 다른 엔진 커맨드는 "엔진 시작 중입니다", `engine_stats`는 `running: false` | H3. |
| 장치 분리 | 명시 없음 | `EngineStats.streamErrors`/`deviceLost` 추가(알림만). 자동 재열기는 아직 없음 | M9. |

M5 수위 제어의 구성:

- **제어량**: lcm(lcm(in_burst, F), out_burst) 주기를 덮는 창(0.1~0.5초)에서 평균과 골(최솟값)을 함께 잰다. 오차 = min(평균 − 목표 평균, 골 − 여유)이다. 위상이 미끄러질 때는 평균이 매끄럽게 따라가고, 위상이 고정된 채 콜백 순서가 뒤집혀 패일 때는 골이 우선한다.
- **보정 방식**: 오차 비례로 하되 최대 500ppm, 10ms당 최대 1샘플, 청크 전체 램프다.
- **시작과 언더런 처리**: 시작 직후 첫 창은 무음으로 흘리며 수위를 재고(priming), 창이 끝나면 오차만큼 한 번에 맞춘 뒤 들리게 시작한다. 언더런이 나면 여유를 입력 방출 하나만큼 늘린다(학습).

### CI 실패(`loopback_loss5_jitter20_drift`) 원인과 수정

CI(windows-latest)에서 출력 연속성 0.93, 8~12초 버퍼 61.6ms(목표 30), 패킷 버림 155회로 실패했다. 원인은 다음과 같다.

1. 깊이를 매 pop에서 **워커가 깨어난 벽시계 시각**으로 쟀다. 느린 러너에서는 워커가 늦게 깨어나 깊이가 실제보다 크게 측정된다.
2. 그러면 패킷 단위 버림(≥3F)이 반복된다.
3. 실제 버퍼가 비어 은닉/재버퍼링이 일어나고, 늦게 온 패킷이 다시 깊이를 키우는 발산 고리가 생긴다.

수정:
- 측정 시각을 소비 카운터 기반의 출력 콜백 시각 추정치(`DeviceClock`: 관측 오프셋의 최솟값 + 500ppm 상향 누설)로 바꿨다. 기상 지연 0~4ms(가끔 20ms)에서 추정 오차는 1ms 미만이다.
- 측정은 버스트당 1회로 줄였다.
- 패킷 단위 버림은 실제 쌓인 양을 확인하고 히스테리시스를 두도록 바꿨다.

같은 조건에 콜백 기상 지연(0~2ms) 버스트를 더한 통합 테스트에서 4초 이후 패킷 버림은 0회였다. 전 코어(14코어)를 같은 우선순위의 바쁜 루프로 포화시킨 상태에서도 15개 통합 테스트가 모두 통과했다. 이때 루프백은 버퍼 26.2ms(목표 25), 패킷 버림 0회, 연속성 100%였다.

포화 실험에서 알게 된 점:
- 가짜 장치 콜백 스레드가 일반 우선순위면 굶어서 수천 번 xrun이 났다. 실제 장치처럼 높은 우선순위로 바꿨다.
- 망을 흉내 내는 테스트 프록시가 굶으면 RTT가 114ms까지 늘어 목표가 상한(80ms)에 닿았다. 실제 망은 로컬 CPU에 느려지지 않으므로 프록시도 높은 우선순위로 바꿨다.
- 두 경우 모두 지터 버퍼 제어는 발산하지 않았다.

### M-5 분석: 로컬 처리 지연과 GOAL 1절

GOAL 1절 정의(`estLatencyMs` = 입력 버퍼 + 프레임 + 출력 링 + 출력 버퍼)로 가짜 장치에서 쟀다.

| 설정 | estLatencyMs | 구성 |
|---|---|---|
| 128 / 2.5ms (GOAL: ASIO ≤ 8ms) | **11.8ms** | 입력 2.67 + 프레임 2.5 + 출력 경로 ≈ 4.0 + 출력 2.67 |
| 128 / 5ms | 14.3ms | 프레임 5ms 몫 증가 |

- **남은 차이(약 4ms)는 구조적이다.** 워커가 출력 콜백 직후 링을 "장치 버퍼 1개 + 청크(64샘플)"까지 채우므로, 링은 다음 콜백까지 거의 장치 버퍼 하나 분량을 들고 있다.
- **8ms 이하에 필요한 것**: 장치 버퍼 2개(5.3ms) + 프레임(2.5ms) = 7.8ms이므로 링 체류가 사실상 0이어야 한다.
- **가능한 방법**:
  - 다음 콜백 직전에 채우는 JIT 리필(스케줄링 지터에 취약)
  - 출력 콜백 안에서 믹스하는 콜백 구동 구조(ASIO 듀플렉스 전용 경로)
  - 둘 다 H2(자체 WASAPI/ASIO 백엔드) 작업과 함께 해야 안전하므로 이번 범위 밖으로 남긴다.

### 설계: 디코드는 워커가 미리, 콜백은 PCM 소스 링에서 필요한 만큼

요구 2의 두 안 중 "디코드는 워커가 미리 하고 콜백은 디코드된 PCM 링에서 JIT로 가져오는 방식"을 택했다.

- **lock-free 디코더/지터 버퍼를 콜백에 두지 않은 이유**
  - 지터 버퍼는 수신 스레드가 삽입하고 상태가 크다(슬롯 1024개, 통계, 보정 상태).
  - Opus 디코드·PLC는 패킷당 수십~수백 µs다. 6인이면 콜백 하나에서 그 몇 배다.
  - 이를 RT 콜백으로 옮기면 할당 없는 디코더 공유와 최악 실행 시간 보장이 새로 필요하다.
- **지연은 같다.** 이전 구조의 지연 원인은 "링이 있어서"가 아니었다. 지터 버퍼 깊이를 **링 앞**(워커가 꺼내는 위치)에서 재서, 링 체류 시간이 깊이 제어 밖에 따로 더해졌기 때문이다.
  - 깊이를 **재생 위치(소스 링 머리)** 에서 재면(`end_burst(now, wall, ahead)`) 소스 링 체류가 목표 안에 들어간다.
  - 그러면 링을 위한 별도 여유가 필요 없다.
- **필요 조건**: 콜백 c 직후 머리 h에서 깊이 D(c) = c − ts(h) − min_transit라 하자.
  - 다음 콜백(c + B)이 [h, h+B)를 실제 데이터로 받으려면 그 패킷이 c + B − guard 전에 와야 한다.
  - 도착 ≤ ts + min_transit + p95이므로 조건은 D ≥ p95 + guard다.
  - 목표 = (ceil(p95/F) + 1)·F ≥ p95 + F이고, F ≥ 2.5ms > guard(1.5ms)이므로 정상 상태에서 만족한다.
  - 장치 버퍼 B는 조건에서 빠진다. 큰 장치 버퍼에서도 은닉이 늘지 않는다.
- **PLC는 비RT에서, 마감 직전에만**: 워커는 받은 데이터로 꺼낼 수 있는 만큼(`JitterBuffer::real_frames`) 소스 링을 `다음 콜백 소비량 + 2청크`까지 미리 채운다.
  - 데이터가 없으면 다음 콜백 예상 시각(`DeviceClock`) − 1.5ms(`DEADLINE_GUARD_US`)가 지난 뒤에만 은닉으로 모자란 만큼 채운다.
  - 늦게 오는 패킷을 마지막까지 기다린다. 이전 구조(콜백 직후 꺼냄)보다 기다리는 시간이 길다.
  - 미리 채우는 양에 상한을 둔 이유: 몰려 온 패킷은 지터 버퍼에 남아야 패킷 단위 버림(실제 쌓인 양 기준)이 동작한다.
- **언더런 시 지연 누적 없음**: 콜백이 소스 링 부족으로 0을 채우면 소스별 `underrun_frames`가 는다. 워커는 그만큼 스트림을 건너뛰어 재생 시각을 장치 시각에 붙인다.
  - 건너뛰지 않아도 깊이 제어(장치 클럭 기준)가 누적을 막기는 한다.
  - 하지만 매 언더런을 샘플 버림 수백 회로 되돌리고 버퍼가 목표 위로 치우친다. 결정적 시뮬레이션에서 건너뛰기 없이 보정 2123회·버퍼 10.64ms, 건너뛰기로 0회·9.39ms였다.
- **소스 슬롯**: 로컬 1개 + 피어 7개. 링은 시작 시 모두 할당한다.
  - 피어가 빠지면 워커가 `SLOT_DRAIN`으로 바꾸고, 콜백이 남은 샘플을 버린 뒤 `SLOT_FREE`로 돌린다. 이전 피어 소리가 새 피어 슬롯에 남지 않는다.
  - 게인·팬·뮤트·모니터는 워커가 원자값으로 넣고, 소스 레벨은 콜백이 알린다.
- **비48k 출력**: 워커가 소스마다 48k → 장치 레이트로 리샘플한다(리샘플러 대기분도 `ahead`에 넣음). 믹스 탭은 장치 레이트로 나오고 탭 스레드가 48k로 되돌린다.
- **로컬(모니터) 소스**: 로컬 FIFO가 입·출력 클럭 차를 흡수하고 자기 수위를 제어한다. 그래서 이전 출력 링 규칙(장치 버퍼 + 청크 + 적응 여유)으로 채운다. 모니터 경로 지연은 이전과 같다(GOAL 지표 밖).

### 루프백 (손실 5%, 지연 U(0, 20ms), 송신 +200ppm, Opus 모노 5ms, 버퍼 128, 콜백 기상 지연 0~2ms, 12초)

기준 커밋(`29552db`)을 같은 머신에서 같은 시험으로 돌려 비교했다.

| 지표 | 기준 커밋 (3회) | P1-0 (13회) |
|---|---|---|
| 버퍼 지연 8~12s / 목표 | 28.7~30.9 / 30ms | 26.5~29.6 / 25~30ms |
| 은닉 프레임 비율 (손실 추정) | 3.79~4.50%, 평균 4.07% (4.2~5.8%) | 3.92~4.83%, 평균 4.45% (4.1~6.0%) |
| 출력 연속성(5ms 창) | 99.94~100%, 무음 구간 0 | 99.89~100%, 무음 구간 0 |
| 4초 이후 패킷 단위 버림 | 0 | 0 |
| xruns | 2 | 2~6 (피어 마감 놓침 = 건너뜀 33~154프레임 포함) |
| B estLatencyMs (128 / 5ms) | 15.7ms | 10.3ms |

- **은닉률이 평균 0.4%p 높다.** 13회 중 5회가 4.5%를 넘었다(최대 4.83%).
  - 원인은 은닉 판단 시점이다. 같은 깊이 목표에서 패킷은 "다음 콜백 − 1.5ms"까지 와야 한다. 이전 구조에서는 "콜백 직후 워커가 꺼낼 때"까지였다.
  - 그래서 p95 바깥 꼬리 패킷에 쓸 여유가 ≈ 2ms 줄었다. 대신 실제 지연이 장치 버퍼 + 청크만큼 줄었다.
  - 마감 여유를 0.6~1.0ms로 줄여 봐도 은닉률은 잡음 범위에서 변하지 않았다. 대신 xrun(마감 놓침)이 14~21회로 늘어 1.5ms로 두었다.
  - 이전 은닉률이 꼭 필요하면 지터 목표에 마감 여유를 더하면 된다(지연 +1.5ms). 사람 판단이 필요하다.
- 연속성 창 1~2개(5ms 창 RMS < 0.15)는 기준 커밋에서도 나온다. 연속 손실의 PLC 감쇠 구간이다. 무음 구간은 양쪽 모두 0이다.
- 은닉은 모두 마감 채움으로 일어났다(마감 채움 ≈ 은닉 수). 지터 없는 링크에서는 마감 채움이 0이다(위 회귀 테스트들).

### 개발 중 잡은 결함(회귀 테스트 있음)

처음 구현은 지터 없는 링크에서 위상에 따라 3초에 1~13회 은닉하고, 그때마다 깊이가 1프레임 늘어 보정이 수백~천여 회 났다. 원인은 두 가지였다.

1. **패킷 꼬리를 못 씀**: 워커가 64샘플 청크 단위로만 미리 꺼냈다. 그래서 FIFO에 남은 패킷 꼬리(< 64)를 마감까지 못 쓰고 은닉했다(예: 링 448 + FIFO 38 ≥ 480인데 은닉). `real_frames`로 꼬리까지 정확히 꺼낸다.
2. **콜백과 워커의 경쟁**: 워커가 재생 카운터를 읽은 뒤 링 점유량을 읽기 전에 콜백이 돌면, 이미 비워진 링을 이전 콜백의 마감 시각과 짝지어 **한 주기 이르게** 은닉했다.
   - 이벤트 기록 분석으로 찾았다. 은닉한 패킷이 실제로는 2~4ms 뒤에 정상 지연(rel ≈ p95)으로 도착했다.
   - 출력 콜백이 시작·끝 카운터(`out_cb_begin`/`out_cb_end`)를 올린다. 워커는 둘이 같고 링을 읽은 뒤에도 그대로일 때만 깊이 측정·마감 판단을 한다.

수정 후 `callback_mix_phase_sweep_no_premature_concealment`(실시간, 3설정 × 3위상)와 `callback_mix_sim_phase_and_buffer_matrix`(결정적, 6조합 × 4위상)에서 은닉·마감 채움·보정이 모두 0이다.

### 자체 WASAPI 백엔드 (`engine/wasapi.rs`)

- **독점**: 이벤트 구동, `GetDevicePeriod` 최소 주기. 포맷은 독점 지원 포맷 중 48k → 44.1k → 96k → 88.2k, f32 → 정수 32(유효 32/24) → 24비트 패킹 → 16비트, 채널은 믹스 포맷 채널 → 2 → 필요 채널, 채널 마스크는 믹스 마스크 → 기본/DIRECTOUT 순이다. `AUDCLNT_E_BUFFER_SIZE_NOT_ALIGNED`면 실패한 클라이언트를 해제한 뒤 장치가 준 크기로 주기를 다시 계산해 새 클라이언트로 재초기화한다. 최소 주기를 거절하면(`AUDCLNT_E_INVALID_DEVICE_PERIOD`/`ENDPOINT_CREATE_FAILED`) 기본 주기로 한 번 더 독점을 시도한다.
- **저지연 공유**: `IAudioClient3::GetSharedModeEnginePeriod`의 최소값으로 `InitializeSharedAudioStream`, 믹스 포맷 그대로. 렌더는 이벤트마다 한 주기만 채워 장치 큐를 한 주기 근처로 둔다.
- **스레드**: 입·출력을 한 스레드(MMCSS "Pro Audio")에서 이벤트 두 개로 처리한다. 둘 다 신호면 캡처가 먼저다(같은 장치 듀플렉스에서 입력→출력 순서 고정). COM 객체는 이 스레드에서 만들고 해제한다.
- **RT 규칙**: 루프에서 하는 일은 WASAPI 호출과 대기, 그리고 `InputRt`/`OutputRt::process`뿐이다(할당·락·로그 없음, 오류는 반환 후 로그). 변환 버퍼(무음 패킷 0, 24비트 패킹 변환)와 MMCSS 등록은 스트림 시작 전에 끝낸다. 열기 로그는 받는 쪽 스레드가 남긴다.
- **오류 분류**(PR #11 H1): 장치 무효화 HRESULT → `deviceLost`. `E_OUTOFMEMORY` → `streamFailed`. 그 밖은 일시 오류: `streamErrors`만 올리고 다음 이벤트에 다시 시도, 같은 방향 연속 4회면 그 스트림 재시작(`streamRestarts`), 성공 없이 재시작 3회 또는 연속 50회면 `streamFailed`. 정책 루프(`drive_loop`)를 장치 I/O(`LoopIo`)와 분리해 가짜 HRESULT 시퀀스로 단위 테스트한다. 이벤트가 100ms 동안 없으면 `GetCurrentPadding`으로 무효화를 확인한다(이벤트가 멈춘 비기본 장치 분리).
- **캡처 플래그**(M2): DATA_DISCONTINUITY → `inputDiscontinuities` + `xruns`(시작 직후 첫 패킷 제외), SILENT → `inputSilentPackets`. 무음 패킷이 변환 버퍼보다 크면 나눠 넘겨 프레임 수를 보존한다.
  - 기본 장치로 연 방향은 감시 스레드가 0.5초마다 기본 장치 ID를 비교해, 바뀌면 `deviceLost`를 켠다.
  - `deviceLost`면 `running=false`라 프론트의 기존 정지 감지가 동작한다. 다시 시작하면 새 기본 장치로 열린다.
- **폴백**: `SystemBackend`가 자체 백엔드 실패 시 (독점, 독점) → (독점, 공유) → (공유, 독점) → (공유, 공유) → cpal 순으로 다시 연다(RT 상태를 돌려받아 재사용). 실제 백엔드는 `EngineStats.backend`로 보인다. 열기가 10초 시간 초과로 포기되면 스레드는 스트림을 시작하지 않는다.
- **장치 목록**: 엔드포인트마다 `wasapiShared` 1개 + 독점 지원 시 `wasapiExclusive` 1개. id는 cpal과 같은 `wasapi::<이름>`이라 저장된 설정이 그대로 맞는다.

## P1-1: 지연 측정 도구 (`engine/measure.rs`, docs/MEASURE.md)

### 설계 요점

- **루프백**: 출력 콜백은 측정 중 믹스 대신 자극 링(사전 할당)만 장치에 쓰고, 입력 콜백은 라우팅된 첫 채널을 녹음 링에 넣는다. 콜백이 하는 일은 요청 번호 비교(원자값) → 첫 프레임 위치 기록 → 링 push/pop뿐이다. 입·출력 카운터를 같은 시간축에 놓는 데 콜백 시각을 쓰지 않는다(시스템콜 금지). 측정 스레드가 카운터를 읽고 나서 벽시계를 읽고, `벽시계 − 카운터/레이트`의 최솟값을 방향마다 잡는다. 입력·출력이 다른 스레드에서 도는 백엔드(cpal WASAPI, 가짜 장치)에서도 위상과 무관하다.
- 왕복 정의 = 소프트웨어 패스스루의 아날로그 입력 → 출력 지연 = 캡처 시각 − 쓰기 시각 + 입력 콜백 크기. 드라이버 보고(ASIO 입력 + 출력 지연)와 같은 기준이다. 가짜 장치는 쓰는 순간 재생하므로(출력 큐 0) 기대값 = 케이블 지연 + 입력 버퍼다.
- `ASIOGetLatencies`는 asio-sys가 바인딩하지 않아 SDK 정적 라이브러리의 C++ 심볼(`?ASIOGetLatencies@@YAJPEAJ0@Z`, asio-sys 바인딩과 같은 맹글링)을 직접 링크한다.
  - `cargo build --features asio --example measure_smoke`가 **링크에 성공**했다. 이 심볼은 PDB에서 해석된 것으로 확인했다(PR #13 M1). 값은 `StreamInfo` → `LoopbackReport.driverInputLatencyMs/OutputLatencyMs` → 패널 표 "드라이버 보고"와 `measure_smoke` 출력으로 나온다.
  - 이 PC에는 Realtek ASIO가 레지스트리에 등록되어 있지만, cpal 열거에서 장치가 나오지 않아("ASIO 장치를 찾을 수 없습니다") 실제 반환값은 읽지 못했다. [사람] Scarlett에서 `measure_smoke asio 5 64`로 0이 아닌 값을 확인한다.
- **에코**: 되돌리기는 수신 스레드에서 디코드 없이 재봉인한다(처리 지연 ≈ 0.1ms, 보고값으로 확인). 그래서 상대의 지터 버퍼·출력은 왕복에 들어가지 않고, 왕복 = 프레임 + 망 왕복 + 내 지터 버퍼다. GOAL "왕복 ÷ 2"의 입→귀는 대칭 가정으로 `mouthToEarMs`에 따로 계산한다.
- 되돌리는 패킷과 내 오디오가 같은 쌍별 키·seq를 쓰면 nonce가 재사용된다. 그래서 Audio seq를 피어별 카운터로 바꿨다(되돌리는 패킷도 같은 카운터를 쓴다). 수신측 지터 버퍼는 seq 연속성만 보므로 프로토콜 호환이다.
- 요청/동의는 Ping 평문(6바이트)으로 싣는다. 릴레이가 엔진 타입 1~6만 중계하므로 새 패킷 타입을 쓰지 않았다(서버·릴레이 수정 없음).

## RT 안전성

- 지연 측정(P1-1): 입력·출력 콜백에 추가된 것은 측정 요청 번호(원자값) 비교, 시작 위치 기록(원자값), 사전 할당 자극/녹음 링 push/pop, 사전 할당 스크래치(256프레임)뿐이다. 측정 중에도 믹스와 탭은 그대로 돌고 장치 기록만 자극으로 바꾼다.
- `engine/rt.rs`의 `process` 경로에는 할당, 락, 로그, 시스템콜이 없다. 출력 콜백의 소스 믹스(P1-0)도 사전할당 소스 링 8개·스크래치·원자값(게인, 레벨, 언더런 프레임, 슬롯 상태, 콜백 시작/끝 카운터)만 쓴다. 스크래치 버퍼(256프레임)는 콜백 클로저가 소유하고, 인덱싱은 `get`/`get_mut`으로 panic을 피한다. 링은 ringbuf 0.4 `HeapRb`(wait-free SPSC)를 쓴다. 오버런 시 `vacant_len()`(원자 읽기)으로 프레임 단위만 기록한다.
- cpal 에러 콜백은 `stream_errors` 원자값만 올리고, 워커가 로그를 남긴다.
- 예외: cpal 백엔드 내부(WASAPI 이벤트 대기 등)는 우리 코드가 아니다. 자체 WASAPI 루프(`engine/wasapi.rs`)는 우리 코드이며 WASAPI 호출·이벤트 대기만 시스템콜로 허용한다(할당·락·로그 없음, 오류는 루프 밖에서 로그).

- **ASIO 경로 전체** (`#[cfg(feature = "asio")]`): 이 PC에 ASIO SDK가 없어 컴파일하지 못했다. cpal 0.15 표준 트레이트 API만 사용했다. 듀플렉스 장치 선택, 48k 우선 선택, 채널 수 선택, 버퍼 범위 판정, 열거 캐시, `ASIO_IN_USE`가 미검증이다.

- **프론트 타입**: `EngineStats`의 `streamErrors`/`deviceLost`/`devicePeriodMs`/`backend`를 `engineApi.ts`에 반영했다(P1-0). UI 표시는 후속이다.

### 그 밖의 통합 테스트

- `engine_start`/`stop` 5회 반복(스레드 join, 멱등 stop)

- 장치 분리 보고(M9)
- 입력 뮤트(출력과 탭 무음, inputLevel 유지, 해제 후 복귀)
- 팬 +1(L 무음, R ×√2)과 레벨 0..1
- ssrc squatting·사칭 패킷 무력화(M7)
- 악의적 descriptor 거부(M8)
- 잘못된 config 거부

## 기타

- 레거시 `audio.rs`/`network.rs` 삭제는 git 상 첫 커밋(`build: 엔진 의존성 교체…`)에 포함됐다(먼저 `git rm`으로 스테이징했기 때문).
- 로컬 FIFO는 시작 후 첫 창(0.1~0.5초) 동안 무음이다(priming).
- 입·출력 콜백이 같은 시각에 몰리는 장치에서 콜백 순서가 뒤집히면 처음 한두 번 끊김이 날 수 있다. 그때 여유를 늘려 이후 안정된다. 실시간 통합 테스트에서는 1024 버퍼 등에서 0~1회 관측됐다. 결정적 시뮬레이션(위상 고정 + 0~1ms 지연)에서는 0회였다.
- 근본 해결(H2와 함께)은 듀플렉스 장치에서 입력 콜백 직후 출력을 채우는 동기 경로다.
