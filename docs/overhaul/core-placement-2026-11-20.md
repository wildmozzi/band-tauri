## 1. 기계와 조건

- CPU: Intel Core Ultra 5 225H — 논리 14 = **P 4 · E 8 · LP-E 2**(`GetSystemCpuSetInformation`: 효율 등급 P = 1, E·LP-E = 0, LP-E는 LLC가 따로). 하이브리드다. P 코어 CPU set은 4개.
- OS: Windows 11(10.0.26300), 전원 계획 "균형 조정".
- 전원: 측정을 시작한 17:15에는 **배터리**(64%)였고 17:18:30~17:19:32 사이에 **AC**로 바뀌었다(1분 간격 전원 로그). 라운드 0은 끔 = 배터리, a = 전환에 걸침, b·a+b = AC라 조건끼리 비교할 수 없다. 그래서 **판정에는 AC 구간(라운드 1~11, 조건당 n = 11)만 쓴다.** 배터리 구간은 실행 1개뿐이라 표를 낼 수 없다(4절 참고 값, [사람]).
- 같은 PC에서 다른 작업자(빌드·시험)와 에디터·브라우저가 돌고 있었다. 조용한 기계가 아니다 — 그래서 교차 순서로 쟀다.
- 도구: `cpu_profile`(`six_peer_full_mesh_cpu` — 한 프로세스에 가짜 장치 엔진 6개, 127.0.0.1 풀메시, 구성마다 예열 3초 + 측정 창 12초), 코어 고정 없음(`BAND_CPU_PIN=none`), 같은 실행파일을 `BAND_THREAD_POLICY`만 바꿔 실행.
- 순서: `scripts/cpu-compare.mjs run --exe off=…@off --exe qos=…@qos --exe pcores=…@pcores --exe both=…@qos+pcores --pin none`. 짝수 라운드는 끔 → a → b → a+b, 홀수 라운드는 역순, 실행 사이 10초. 본 측정 10라운드(17:15~18:25) + AC 추가 2라운드(18:25~18:41), 이어서 경합 확인(18:41~18:48).

읽기(PR #245 리뷰 M2):

- 정책을 걸면 xrun이 **줄어든 구성도 있고 늘어난 구성도 있다.** 무거운 구성(강제 Opus 2개)과 Opus 2.5ms는 끔에서 거의 매번 나던 xrun이 a·a+b에서 줄었다. 반대로 **PCM16 2.5ms는 끔이 11번 모두 0인데 a+b는 3번(6·8·3), b는 3번(31·3·6), a는 2번** 났다. PCM16 5ms도 끔 1번 → b 4번 · a+b 2번이다.
- PCM16 2.5ms의 끔 0/11 대 a+b 3/11은 Fisher 양측 p ≈ 0.21(리뷰 계산)이라 차이라고 말할 수 없지만, "흔들림 안"이라고 단정할 근거도 없다.
- b 단독의 "PCM16 2.5ms + 강제 Opus"는 2번(라운드 5·6) 528·492로 튀었고 a+b는 최대 3이었다. 2/11 대 0/11(Fisher p ≈ 0.48, 리뷰 계산)이고 원인을 확인하지 않았으며 a+b가 그 꼬리를 막는 기제도 없다 — **"b에 있는 꼬리가 a+b에는 없다"고 말할 수 없다.** a 단독도 Opus 2.5ms에서 한 번 76이 나왔다.
- 조건당 측정 시간은 구성마다 12초 × 11 = 132초다. 평균 비교에는 충분하지만 드문 꼬리(xrun 폭주)를 배제하기에는 짧다. 꼬리는 야간 Soak(6엔진 60분)를 정책 끔/켬으로 돌려 봐야 한다(7절).

## 6. 판정 — 옵션으로 넣고 기본은 끔

### 측정이 말하는 것

- **a+b**: 6구성 모두 워커 CPU가 끔 대비 −18~−28%이고 95% 구간 상한이 −10%보다 아래다. `iter_body` p99도 6구성 모두 −22~−40%로 구간이 0 밖이다. 리뷰의 재계산(라운드별 비율 정의, 라운드 0 포함, 36개 비교 Bonferroni 보정)으로도 6구성 모두 0 밖이었다.
- **b 단독**: 6구성 모두 구간이 0 밖(워커 CPU −16~−24%). a+b와 b의 차이는 3구성(Opus 5ms, 강제 Opus 2개)에서 a+b 쪽이 −9~−11% 더 낮고 나머지는 흔들림 안이다.
- **a 단독**: P 비율을 5~13% → 62~75%로 올리지만 워커 CPU는 6구성 중 4개에서만 구간이 0 밖이다(Opus 5ms·PCM16 5ms는 걸침). 쌍별 차를 (후 − 전) / **그 라운드의 전**으로 정의하면 "PCM16 5ms + 강제 Opus"도 [−30.1, +0.6]으로 걸쳐 3개가 된다(리뷰 L3 — 이 문서의 표는 `cpu-compare.mjs` 정의인 (후 − 전) / 전 평균이다. a+b·b의 결론은 어느 정의로도 같다). `iter_body` p99는 6구성 모두 줄었다(−12~−32%).
- **들리는 지표는 차이가 없다.** 최대 은닉률은 모든 조건이 평균 0.2% 아래다. 이 측정이 보인 이득은 CPU 여유와 반복 본문 꼬리이고, GOAL 지표(지연·끊김)의 개선은 보이지 않았다.
- xrun은 구성에 따라 줄기도 늘기도 했다(3절 표). 꼬리 위험은 이 표본 크기로 판단할 수 없다.

### 기본으로 켜지 않는 이유

1. **`SetThreadSelectedCpuSets`는 "선호"가 아니다 — 스레드는 고른 집합 안에 머문다**(리뷰 H1). 리뷰어가 이 기계에서 확인했다: 보통 우선순위 바쁜 스레드 8개에 P 코어 4개 CPU set을 걸면 E 코어 8개가 비어 있어도 P 비율 100%, 합계 CPU가 6.95 → 3.41 코어였다. 이 문서의 5절(경합 확인)에서도 a+b의 P 비율은 100%였다 — 나빠지지 않은 것은 엔진 스레드가 MMCSS로 **우선순위가 높아 밀어냈기** 때문이지 E 코어로 넘어갔기 때문이 아니다. 그래서 P 코어를 **같거나 높은 우선순위** 부하(DAW·다른 오디오 앱의 MMCSS "Pro Audio" 스레드, 게임)가 채우면, 정책이 없을 때는 빈 E 코어로 갈 수 있던 워커가 b에서는 갈 수 없다. **그 상황은 재지 않았다.**
2. **효과 크기가 과대평가됐을 수 있다**(리뷰 M3). 오늘 끔의 워커 P 비율은 5~13%인데 1단계(11-17, 조용한 기계)의 끔은 35~58%였다. 측정 프로세스가 창 없는 백그라운드 프로세스였고 다른 작업자가 같은 PC를 쓰던 것이 달랐을 수 있지만 **원인은 확인하지 않았다.** 리뷰어가 끔·a 실행으로 "워커 CPU ~ 워커 P 비율"을 회귀해 끔이 P 45%였다고 가정하면 a+b의 감소는 대략 −13~−21%(측정값의 약 2/3)였다. 반대 방향 근거: 오늘 끔의 워커 CPU 절대값(Opus 2.5ms 13.86%)은 1단계 끔(14.08%)과 비슷하다. 어느 쪽이든 "끔이 얼마나 나쁜가"는 날마다 다르고, 이 측정이 말하는 것은 "정책을 걸면 워커가 P 코어에 놓이고 그때 CPU가 낮다"까지다.
3. **실제 앱 근거가 없다.** 측정은 한 프로세스에 엔진 6개(워커 6 + 수신 6이 P 4개를 나눔 — a+b에 불리)이고 창 없는 백그라운드(끔에 불리)다. 엔진 1개·창이 앞에 있는 실제 앱에서 어느 쪽이 큰지 모른다. 1단계 문서는 기본값 변경을 사용자 결정으로 적었다.
4. **소비 전력·발열·배터리 시간을 재지 않았다.** 두 정책 모두 전력을 늘리는 방향이다. 배터리 구간은 실행 1개뿐이다(4절).
5. 기계 1대(4P + 8E + 2LP-E)다.

### 이 PR이 넣는 것

- 두 정책을 **옵션(기본 끔)**으로: 엔진 설정 `EngineConfig.threadPolicy = { highQos, preferPCores }`(오디오 설정 "고급 — 실험적" 토글 2개, 엔진을 다시 시작하면 적용)와 환경변수 `BAND_THREAD_POLICY` = `off` | `highqos` | `pcores` | `both`(있으면 설정보다 우선, 제품 빌드에서도 읽는다).
- 기본(둘 다 끔)에서는 워커·수신 스레드가 OS 호출 없이 이 PR 전과 같은 경로로 돈다(시험으로 고정).
- b는 **물리** P 코어가 4개 이상일 때만 건다(리뷰 M1 — 하이퍼스레딩 2P4T + 8E는 논리 프로세서가 4개여도 걸지 않는다). 다른 프로세스가 독점한 CPU set은 고르지 않는다(리뷰 L2). 주차(Parked)된 코어는 가리지 않는다(실행 중 바뀌는 값). 프로세서 그룹이 둘 이상인 기계(논리 64 초과)는 시험하지 않았다.
- 적용 결과는 `EngineStats.threadPolicy`와 진단 내보내기에 남는다(`pending` | `off` | `applied` | `failed` | `skipped`).
