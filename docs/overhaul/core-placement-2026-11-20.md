# 하이브리드 CPU 엔진 스레드 코어 배치 대책 — 교차 측정과 판정 (P1-21 2단계, 2026-11-20)

- 관련: [core-placement-2026-11-17.md](core-placement-2026-11-17.md)(1단계 — 배치 기록, HighQoS n = 3은 결론 없음), [cpu-measure.md](cpu-measure.md)(측정 방법), 계약 [native-engine-design.md](native-engine-design.md) 4절 `threadPolicy`.
- 원자료: [core-placement-2026-11-20-runs.csv](core-placement-2026-11-20-runs.csv)(`set` = `ac` 라운드 1~11, `r0-battery-mixed` 라운드 0, `hog14` 경합 확인).

## 1. 기계와 조건

- CPU: Intel Core Ultra 5 225H — 논리 14 = **P 4 · E 8 · LP-E 2**(`GetSystemCpuSetInformation`: 효율 등급 P = 1, E·LP-E = 0, LP-E는 LLC가 따로). 하이브리드다. P 코어 CPU set은 4개.
- OS: Windows 11(10.0.26300), 전원 계획 "균형 조정".
- 전원: 측정을 시작한 17:15에는 **배터리**(64%)였고 17:18:30~17:19:32 사이에 **AC**로 바뀌었다(1분 간격 전원 로그). 라운드 0은 끔 = 배터리, a = 전환에 걸침, b·a+b = AC라 조건끼리 비교할 수 없다. 그래서 **판정에는 AC 구간(라운드 1~11, 조건당 n = 11)만 쓴다.** 배터리 구간은 실행 1개뿐이라 표를 낼 수 없다(4절 참고 값, [사람]).
- 같은 PC에서 다른 작업자(빌드·시험)와 에디터·브라우저가 돌고 있었다. 조용한 기계가 아니다 — 그래서 교차 순서로 쟀다.
- 도구: `cpu_profile`(`six_peer_full_mesh_cpu` — 한 프로세스에 가짜 장치 엔진 6개, 127.0.0.1 풀메시, 구성마다 예열 3초 + 측정 창 12초), 코어 고정 없음(`BAND_CPU_PIN=none`), 같은 실행파일을 `BAND_THREAD_POLICY`만 바꿔 실행.
- 순서: `scripts/cpu-compare.mjs run --exe off=…@off --exe qos=…@qos --exe pcores=…@pcores --exe both=…@qos+pcores --pin none`. 짝수 라운드는 끔 → a → b → a+b, 홀수 라운드는 역순, 실행 사이 10초. 본 측정 10라운드(17:15~18:25) + AC 추가 2라운드(18:25~18:41), 이어서 경합 확인(18:41~18:48).

## 6. 판정

- **a+b(HighQoS + P 코어 선호)를 기본 켬으로 바꾼다.** 6구성 모두에서 워커 CPU가 끔 대비 −18~−28%이고 95% 구간 상한이 −10%보다 아래다. `iter_body` p99도 6구성 모두 −22~−40%로 구간이 0 밖이다. 최대 은닉률은 모든 조건이 평균 0.2% 아래로 차이가 없다. xrun은 무거운 구성(강제 Opus)에서 끔 15·8 → a+b 1·2로 줄었고, 가벼운 구성은 모든 조건이 평균 0~2로 흔들림 안이다.
- **b 단독**도 6구성 모두 구간이 0 밖이다(워커 CPU −16~−24%). a+b와 b의 차이는 3구성(Opus 5ms, 강제 Opus 2개)에서 a+b 쪽이 −9~−11% 더 낮고 나머지는 흔들림 안이다. a+b가 b보다 나쁜 구성은 없고, b 단독은 가장 무거운 구성에서 xrun이 튄 실행이 2번 있었지만 a+b는 없었다(3절). 그래서 둘을 함께 켠다.
- **a 단독**은 P 비율을 5~13% → 62~75%로 올리지만 워커 CPU는 6구성 중 4개에서만 구간이 0 밖이고(Opus 5ms·PCM16 5ms는 걸침) 효과도 b보다 작다. `iter_body` p99는 6구성 모두 줄었다(−12~−32%).
- 1단계(11-17, AC)의 끔은 워커 P 비율이 35~58%였는데 오늘 끔은 5~13%다. 측정 프로세스가 창 없는 백그라운드 프로세스로 실행되고 다른 작업자가 P 코어를 쓰던 것이 달랐을 수 있지만 **원인은 확인하지 않았다.** 그래서 "끔이 얼마나 나쁜가"는 날마다 다르고, 이 측정이 말하는 것은 "정책을 걸면 워커가 P 코어에 놓이고 그때 CPU가 낮다"까지다.

### 한계

- 측정은 한 프로세스에 엔진 6개(워커 6 + 수신 6 스레드가 P 코어 4개를 나눠 씀)다. 실제 앱은 엔진 1개이고 창이 앞에 있으면 Windows가 원래 P 코어를 더 주므로, 실제 앱에서 끔과의 차이는 이보다 작을 수 있다.
- 기계 1대(4P + 8E + 2LP-E). P 논리 프로세서가 4개 미만인 기계는 정책을 걸지 않게 했다(`MIN_P_LOGICAL`, `skipped`) — 좁은 집합에 묶는 쪽이 나은지 근거가 없다.
- CPU set은 하드 affinity가 아니지만 Windows는 고른 집합을 거의 그대로 지킨다(a+b·b에서 P 비율 100%). P 코어가 같은 우선순위 부하로 가득 찬 상황은 재지 않았다.
- 소비 전력은 재지 않았다. HighQoS와 P 코어 선호는 배터리 사용 시간을 줄일 수 있다.

## 7. [사람] 확인

1. **배터리 전원**에서 같은 교차 측정(조건당 n ≥ 10): 정책 효과와, 가능하면 소비 전력·배터리 시간 차이.
2. 하이브리드 노트북에서 **실제 앱**으로 10분 합주한 뒤 진단 내보내기: `engine.json` `lastStats.threadPolicy`가 `applied`인지, 타임라인 `corePlacement`가 P에 몰리는지, `cpu.workerPct`·xrun·은닉이 이전 빌드보다 나빠지지 않았는지(AC·배터리 각각).
3. DAW 같은 다른 프로 오디오 앱을 함께 켠 상태에서 끊김이 늘지 않는지 청취 확인.
4. 다른 하이브리드 기계(예: 12~14세대 P+E, Lunar Lake 4P+4LP-E, AMD Zen5/Zen5c)에서 `threadPolicy` 값과 워커 CPU.
