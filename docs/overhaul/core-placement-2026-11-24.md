## 1. 넣은 것 — P 코어 정책 넷 중 하나

| `pCoreMode` | `BAND_THREAD_POLICY` 낱말 | 하는 일 | 강제성 |
|---|---|---|---|
| `off`(기본) | (없음) | 걸지 않는다 | — |
| `pin` 고정(2단계) | `pin`(옛 `pcores`) | `SetThreadSelectedCpuSets`(P 코어 CPU set) | 집합 안에 머문다 |
| `prefer` 선호 힌트(2안) | `prefer` | `SetThreadIdealProcessorEx`(P 코어 하나를 선호 프로세서로) | 힌트 — 옮겨질 수 있다 |
| `adaptive` 조건부 고정(3안) | `adaptive` | `pin`처럼 묶고, 끊김·기상 지연이 늘면 풀고 안정되면 다시 묶는다 | 묶인 동안은 `pin`, 풀린 동안은 `off` |

설정은 `EngineConfig.threadPolicy.pCoreMode`(오디오 설정 "고급"의 선택 상자 — 실험적), 환경변수는 `highqos+prefer`처럼 `+`로 잇는다. 2단계 저장값(`preferPCores: true`)과 환경변수 값(`off`·`highqos`·`pcores`·`both`)은 뜻이 그대로다(`preferPCores: true` = `pin`).

## 2. 2안 — 어떤 API가 soft인가 (문서 확인 + 실측)

Microsoft Learn 문서를 직접 확인했다(2026-11-24).

| 후보 | 문서의 말 | 실제 |
|---|---|---|
| CPU set을 스레드에(`SetThreadSelectedCpuSets`) | "CPU Sets provide APIs to declare application affinity in a 'soft' manner that is compatible with OS power management." / "A thread affinitized to a given CPU Set will **typically** execute on one of the processors in its list of selected CPU Set IDs." / "If a thread is assigned to multiple valid CPU Sets, it will run on one of the corresponding processors according to its priorities and the priorities of competing threads on those processors." | **집합 밖으로 나가지 않는다.** 바쁜 스레드 8개에 P 코어 4개 CPU set을 걸면 E 8개가 비어 있어도 P 100%, 쓴 코어 3.8~4.0(아래 프로브, 2단계 리뷰 H1과 같다). 문서의 "soft"는 전원 관리(코어 주차)·독점 집합과의 관계를 말하는 것으로 보이고, 포화 때 넘쳐 나간다는 뜻이 아니다 |
| 프로세스 기본 CPU set(`SetProcessDefaultCpuSets`) | "Threads that are created, which don't have CPU Sets explicitly set using SetThreadSelectedCpuSets, will inherit the sets specified by SetProcessDefaultCpuSets automatically." | 같은 기제를 프로세스 전체(UI·제어 스레드 포함)에 건다 — 더 넓게 묶일 뿐 soft해지지 않는다. 쓰지 않는다 |
| 선호 프로세서(`SetThreadIdealProcessorEx`) | "Specifying a thread ideal processor provides a hint to the scheduler about the preferred processor for a thread. The scheduler runs the thread on the thread's ideal processor when possible." / (Multiple Processors) "This does not guarantee that the ideal processor will be chosen but provides a useful hint to the scheduler." | **soft다.** 바쁜 스레드 8개에 걸어도 E로 넘쳐 쓴 코어 7.8(프로브) — 걸지 않았을 때와 같다 |
| QoS(`ThreadPowerThrottling`) | "On platforms with heterogeneous processors, the QoS of a thread may restrict scheduling to a subset of processors, or indicate a preference for a particular class of processor." | HighQoS(①, 이미 기본 켬)가 이쪽이다 — P 선호를 더 세게 말하는 값은 문서에 없다 |

그래서 2안은 **선호 프로세서**다. 문서는 하이브리드 CPU에서의 동작이나 시스템이 선호 프로세서를 다시 고르는지는 말하지 않는다 — 힌트가 실제 배치를 얼마나 바꾸는지는 본측정의 `corePlacement`로 본다(연기 시험에서는 조용할 때 워커 P 비율이 끔보다 높았고, 경합에서는 끔처럼 E로 넘어갔다 — 5절, n = 2).

구현: P 코어 논리 프로세서 목록을 돌아가며 스레드마다 하나씩 고른다(물리 코어마다 하나씩 먼저, 하이퍼스레딩 형제는 뒤 — 프로세스 전체 카운터). 걸 코어의 조건은 고정과 같다(하이브리드, 쓸 수 있는 물리 P 코어 4개 이상 — 아니면 `skipped`).

## 3. 3안 — 조건부 고정

판단 기준·이력·다시 묶는 조건은 설계 문서 1.1절 "P 코어 정책"의 `adaptive` 항목이 계약이다. 요약:

- 판단은 **워커가 반복 끝에서**(RT 콜백 밖) 1초 창마다 — 순수 상태 기계 `sys::pin_adapt::Decider`. 적용은 **각 스레드가 자기에게**(워커는 반복마다, 수신 스레드는 패킷마다 원자값 하나를 읽고 바뀌었을 때만 OS 호출 한 번). `rt.rs`·cpal 콜백 경로는 건드리지 않았다(RT 콜백은 전부터 올리던 xrun 카운터를 올릴 뿐이다).
- 신호: ① xrun 증분(원자값 읽기) ② 워커의 멈칫 수(2ms 이상 늦게 깸 + 본문 3ms 이상) ③ P 코어 포화 추정(유휴 스레드 사이클, 창마다 시스템콜 하나).
- 풀기: 심한 창(xrun ≥ 8 또는 멈칫 ≥ 40) 하나, 또는 나쁜 창(xrun ≥ 2 또는 멈칫 ≥ 5 — P 코어 바쁨 ≥ 90%면 xrun ≥ 1 또는 멈칫 ≥ 2) 연속 2개.
- 다시 묶기: 기다림(처음 10초)이 끝나고 + 좋은 창 연속 5개 + (추정이 있으면) P 코어 바쁨 < 60%.
- 되풀이 억제: 묶고 15초 안에 또 풀리면 기다림 두 배(최대 320초), 60초를 버티면 10초로.
- 시험: 판단 쪽 10개(`sys::pin_adapt::tests` — 문턱, 연속 조건, 기다림·좋은 창·P 바쁨 조건, 두 배 늘기와 되돌리기, 한 시간 16번 상한, 창 누적, 공유 상태), 적용 경로(`adaptive_slot_releases_and_rebinds_on_verdict`, 실제 OS 호출 `os_policy_applies_on_this_thread`), 할당 0(`adaptive_path_does_not_allocate`), 진단 타임라인이 풀고 묶은 줄만 남기는지.

## 4. 측정 도구 — `policy_matrix`

`cargo run --release -p band-engine --example policy_matrix` 한 명령으로 정책 4종(모두 HighQoS 켬) × 환경 2종 × 구성 6개를 라운드 교차로 재고 `results.md`·`results.json`·`runs.jsonl`을 남긴다. 측정 본체는 2단계가 쓴 `cpu_profile`의 6엔진 풀메시 그대로다(`tests/support/mesh_cpu.rs`로 옮겨 함께 쓴다).

- **경합 환경**: 다른 프로세스가 P 코어 논리 프로세서 수만큼(225H는 4개) 바쁜 스레드를 띄운다 — 스레드마다 P 코어 CPU set에 묶이고 **엔진 스레드와 같은 MMCSS "Pro Audio"**로 등록한다. 2단계 6절 1번("P 코어를 같거나 높은 우선순위 부하가 채우면" — 재지 않은 상황)이다. 부하가 실제로 쓴 코어 수와 MMCSS 등록 수를 결과에 싣는다.
- **프로브**: 측정 앞에 선호 힌트의 강제성을 본다(2절 표의 "실제" 칸).
- 인자: `--rounds` 또는 `--minutes`(총 소요 시간에 맞춰 라운드 수), `--window-s`(기본 20초), `--configs`·`--policies`·`--envs`(부분 실행), `--hog-threads`·`--hog-duty`·`--hog-prio`, `--dry-run`(계획·예상 시간만).

## 5. 연기 시험 — **오염된 환경의 동작 확인용**

`policy_matrix --rounds 2 --window-s 6 --warmup-s 2 --cooldown-s 2 --configs opus2.5,pcm5`(release). **다른 작업자의 빌드·e2e가 같은 PC에서 돌고 있었다.** 조건당 실행 2개, 창 6초다 — 16실행이 모두 끝까지 돌았고 표가 채워지는 것을 확인했다. 아래 값으로 정책을 고르지 않는다.

읽을 수 있는 것은 "도구가 구분은 한다"까지다: 경합에서 고정은 P 100%에 머물며 `iter_body` p99와 은닉이 뛰었고, 조건부 고정은 실행마다 한 번 풀려(P 코어 바쁨 100%) 끔과 같은 배치가 됐고, 선호 힌트는 끔처럼 E로 넘어갔다. 크기·유의성은 본측정이 말한다.

- 시작(UTC) 20261124-031041, 소요 5분 16초
- 기계: 논리 14 = P 4 · E 8 · LP-E 2 (효율 등급 [0, 1], P 코어 CPU set 4개)
- 2라운드(짝수 라운드 정순, 홀수 라운드 역순), 구성마다 예열 2s + 측정 창 6s, 실행 사이 2s
- 정책(모두 HighQoS 켬): 끔 = `highqos`, 고정 = `highqos+pin`, 선호 힌트(2안) = `highqos+prefer`, 조건부 고정(3안) = `highqos+adaptive`
- 경합 환경: 다른 프로세스의 바쁜 스레드 4개(P 코어 CPU set에 묶음, 우선순위 mmcss, 바쁜 비율 1)
- 전원(라운드마다 기록): ac
- **표본이 적다(라운드 2)** — 도구가 도는지 보는 용도다. 차이를 말할 수 없다

값은 평균 ± 표준편차 (중앙값), 표본 하나면 값 하나. 6엔진 평균(xrun은 6엔진 합, 최대 은닉은 6엔진 최대).

### 5.0 선호 힌트가 soft한지 — 보통 우선순위 바쁜 스레드 8개

| 스레드에 건 정책 | 프로세스가 쓴 코어 수 | P (%) | E (%) | LP-E (%) | 적용 결과 |
|---|---|---|---|---|---|
| off | 7.58 | 57.8 | 42.2 | 0.0 | `{"highQos":"off","pCores":"off"}` |
| prefer | 7.80 | 54.1 | 45.9 | 0.0 | `{"highQos":"off","pCores":"applied"}` |
| pin | 3.77 | 100.0 | 0.0 | 0.0 | `{"highQos":"off","pCores":"applied"}` |

고정(`pin`)이면 P 100%에 쓴 코어 수 ≈ P 코어 수, soft면 스레드가 E로 넘쳐 쓴 코어 수 ≈ 스레드 수다.

## 6. 본측정 — 코디네이터가 조용한 시간에

```sh
cd client/src-tauri
cargo run --release -p band-engine --example policy_matrix -- --dry-run     # 계획·예상 시간 확인
cargo run --release -p band-engine --example policy_matrix -- --out policy-matrix-main
```

- 기본값 그대로: 10라운드 × 환경 2 × 정책 4 × 구성 6, 예열 3초 + 창 20초 — **약 3시간 17분**(225H 어림. 시간이 모자라면 `--minutes 120` → 6라운드, 약 2시간).
- 조건: 다른 작업자·빌드·브라우저를 모두 멈추고, **AC 전원**(결과 머리의 "전원" 줄이 `ac` 하나여야 한다 — 도중에 바뀌었으면 그 라운드부터 따로 본다), 창을 앞에 둘 필요는 없다(자식 프로세스는 창이 없다 — 2단계와 같은 조건).
- 경합 환경이 도는 동안 PC가 느려진다(P 코어 4개가 실시간 우선순위로 찬다).
- 결과 폴더(`policy-matrix-main`)의 `results.md`를 이 문서 뒤에 새 문서로 붙이고 `results.json`·`runs.jsonl`을 원자료로 둔다.

판정에서 볼 것(제안):

1. **경합에서 나빠지지 않는가**(우선 조건): 경합 표의 xrun 원값·최대 은닉·`iter_body` p99가 끔보다 나쁘지 않은 정책만 후보. 연기 시험대로라면 고정은 여기서 탈락한다.
2. **조용할 때 얻는 것이 있는가**: 조용함 표의 워커 P 비율·워커 CPU·`iter_body` p99가 끔보다 뚜렷이 나은가(같은 라운드끼리 쌍별 차 — `results.json`의 `runs[].rows`).
3. 조건부 고정: 조용함에서 "푼 횟수"가 0에 가까운가(괜히 풀지 않는가), 경합에서 풀린 뒤 지표가 끔 수준으로 돌아오는가. 푼 횟수가 조용함에서도 잦은 구성(무거운 "+opus" 구성 — 평소에도 xrun이 난다)이 있으면 문턱을 다시 본다.
4. 선호 힌트: 조용함에서 P 비율이 끔보다 오르는가. 오르지 않으면 2안은 효과 없는 안이다.
5. 넷 다 뚜렷하지 않으면 기본값은 끔 유지다(2단계 측정에서 HighQoS만으로 워커 P 비율이 62~75%였다).

## 7. 리스크와 [사람] 확인

- **본측정 전이다.** 이 PR은 옵션과 도구만 넣는다. 기본값(P 코어 정책 끔)에서는 워커 반복에 분기 하나, 수신 루프에 분기 하나가 늘 뿐이다.
- 3안의 문턱(2ms·3ms·xrun 2/8·멈칫 5/40·90%/60%·10~320초)은 225H 한 대의 실측 꼬리에서 잡은 값이다. 다른 기계(느린 4코어 하이브리드, 2P+8E는 `skipped`)에서 맞는지 모른다.
- 3안은 증상의 원인을 가리지 못한다 — 고정과 무관한 xrun에도 푼다(안전한 쪽이지만 "괜히 풀림"이 잦으면 고정의 이득을 잃는다). 판단 창이 1초라 포화 시작 뒤 1~2초의 끊김은 겪는다.
- 2안은 문서상 힌트일 뿐이고 하이브리드 CPU에서의 효과는 문서에 없다. Windows 버전·전원 계획에 따라 달라질 수 있다.
- P 코어 포화 추정(`QueryIdleProcessorCycleTimeEx`)은 x86_64 Windows·프로세서 그룹 하나에서만 값을 낸다. ARM64 Windows·논리 64 초과 기계에서는 xrun·멈칫과 기다림만으로 판단한다(시험하지 않은 구성).
- 경합 부하는 "완전히 바쁜 MMCSS 스레드 4개"라는 한 가지 모양이다. 실제 DAW는 버스트성이고 MMCSS가 오래 도는 스레드를 낮출 수 있다(`SystemResponsiveness`) — `--hog-duty`로 바꿔 볼 수 있지만 **실제 DAW를 켠 합주는 [사람]** 이다(2단계 7절 1번 그대로).
- **[사람]** 실제 앱(엔진 1개)에서 방식별 10분 합주: 🎛️ 설정 "고급" → "엔진 스레드를 고성능 코어에 두기"를 바꿔 가며 진단 zip의 `lastStats.threadPolicy`(`pCoreMode`·`adaptive`)·타임라인 `corePlacement`·xrun·은닉 비교. 조건부 고정은 DAW를 함께 켰다 껐을 때 토글 아래 줄이 "지금은 풀려 있습니다…" ↔ "적용됨 — …묶어 두었습니다"로 바뀌는지.
- **[사람]** 배터리 전원에서의 같은 측정(2단계부터 남은 항목).
