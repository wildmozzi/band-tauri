# 워커 CPU 정밀 측정 — 조용한 기계, 교차 10회 (P1-14c, 2026-11-17)

- 관련: [../ARCHITECTURE-DECISIONS.md](../ARCHITECTURE-DECISIONS.md) D6(동작 불변 증거), [engine-stage2b-design.md](engine-stage2b-design.md) 6.2절. 부록: 측정 패치 [cpu-quiet-2026-11-17-patch.diff](cpu-quiet-2026-11-17-patch.diff), 실행별 원자료 [cpu-quiet-2026-11-17-runs.csv](cpu-quiet-2026-11-17-runs.csv)(m1·m2 80실행 × 6구성 = 480행).

배경: #137(②b-2) 리뷰 M1 — Opus 2.5ms 워커 CPU 평균 11.80→12.78%(+0.98%p, 약 +8%) 치우침이 실제인지. 그리고 "동시 작업 잡음으로 ±5% 판정 불가"로 미룬 PR들(#142 ⑧a, #143 ②b-6b, #147 ⑧b, #151 ⑥-3, #152 ⑥-5, #153 ⑥-6, #160 ⑩-1, #161 ⑩-2, #175 워커 루프 할당 0)의 누적 영향.

## 결론

- **A(②b-2 전 `17676ca` → 후 `da39adb`)**: 코어 고정 측정에서 6구성 모두 워커 CPU 쌍별 차 평균 **−4.6 ~ +0.3%**, Opus 2.5ms **−1.25% (95% t 구간 −4.86 ~ +2.36)**. #137의 +8% 치우침은 **재현되지 않는다** — 증가 쪽 회귀가 없다.
- **B(R-1 ②b 시작 전 `67804b7` → 현재 develop `0d49f59`)**: 6구성 모두 쌍별 차 평균 **−2.3 ~ +1.2%**, 95% t 구간 상한 최대 **+2.90%**(Opus 5ms). **R-1 ②b~⑩·#175 누적에서 증가 쪽 +5%를 넘는 회귀가 없다**(6구성 95% t 구간 상한이 모두 +5% 아래). 그래서 C(이분 탐색)는 하지 않았다.
- **치우침은 코드보다 스레드가 어느 코어에 놓이느냐로 설명된다(정황).** 이 기계(Intel Core Ultra 5 225H)는 P 4·E 8·LP-E 2 혼합 코어다. 코어를 고정하지 않으면 실행이 두 상태로 갈린다: Opus 2.5ms 워커 CPU **≈ 15~17%(높은 상태)** 대 **≈ 9.6~10.5%(낮은 상태)**(1.6배). 어느 상태가 되는지는 실행파일보다 시각(라운드)이 더 잘 설명하고, n = 10으로는 실행파일 사이 차이를 가를 수 없다(아래 2절). LP-E 코어(12·13)만 빼고 고정하면 한 상태로 모이는 것이 근거이고, 어느 스레드가 느린 코어에 놓이는지는 가르지 않았다(4절 2번). #137의 A/B/A 3회·4회 측정은 이 두 상태가 섞인 표본이다.
- 판정 기준(쌍별 차 95% 구간이 ±5% 안 = "안", 밖 = "밖", 걸치면 "걸침"): 코어 고정 측정에서 **"밖"은 0개**. "걸침"은 전부 구간 아래쪽(감소 쪽)이 −5%를 넘거나, 실행 1회의 튀는 값(아래 각주) 때문이다. 증가 쪽 상한이 +5%를 넘은 것은 A의 "+5피어 Opus 강제" 두 구성(+5.43%·+5.47%) 뿐이고 둘 다 평균은 +0.31%·−4.56%다. 튄 실행 1라운드씩을 빼면(n = 9, t = 2.306) 둘 다 "안"이다: 2.5ms 강제 −1.80% [−3.96, +0.37], 5ms 강제 −0.21% [−2.22, +1.80](각주¹). 그래서 이 문서의 주장은 "±5% 안"이 아니라 **"증가 쪽 +5% 회귀 없음"**이다 — 12개 중 "안" 7·"걸침" 5이고, 걸침 중 3개는 감소 쪽으로만 −5%를 넘는다.
- **한계 — 코어 고정 판정은 반복당 비용만 본다.** m2는 스레드가 느린 코어에 놓일 확률을 실험에서 지운다. 실제 앱은 고정 없이 돌므로, 코드 변화가 그 확률(예: 수면 패턴에 따른 전원 조절·EcoQoS 판정)을 바꾸는 회귀는 이 측정 범위 밖이다. m1의 높은 상태 횟수(아래 2절)는 실행파일 사이 차이를 보이지 않지만 n = 10이라 그런 회귀가 없다는 증거도 못 된다. 이 부분은 4절 2번(스레드별 코어 배치 기록)이 맡는다.

## 2. 코어 고정 없음(m1) — 두 상태

Opus 2.5ms 워커 CPU 평균(6엔진, %, 1코어), 12% 기준으로 가름:

| 실행파일 | 높은 상태(횟수, 평균) | 낮은 상태(횟수, 평균) |
|---|---|---|
| `17676ca` | 5회, 16.02 | 5회, 9.96 |
| `da39adb` | 7회, 15.48 | 3회, 10.44 |
| `67804b7` | 8회, 15.49 | 2회, 9.94 |
| `0d49f59` | 7회, 14.75 | 3회, 9.81 |

- 상태 안에서는 실행파일 사이 차이가 작고(낮은 상태 9.8~10.4), 상태 사이 차이(1.6배)가 지배한다. "+5피어 Opus 강제"는 15 대 30~34(2배)로 더 크다. 라운드 0~3은 16회 모두 높은 상태, 라운드 4~9는 24회 중 11회다 — 실행파일보다 시각(OS 스케줄링·전원 상태)이 상태를 더 잘 설명한다. 실행파일별 높은 상태 5·7·8·7회(10회 중)는 서로 가를 수 없다(예: 5/10 대 8/10, Fisher 정확 검정 양측 p ≈ 0.35). 다만 n = 10이라 "실행파일과 무관"까지 보인 것은 아니다(결론의 한계 항목).
- 높은 상태에서는 `iter_body` p99도 740~1,090µs(낮은 상태·m2는 410~460µs), 콜백 p99도 20~22µs(m2 13~15µs)다. 워커·수신 스레드가 느린 코어(LP-E 추정)에 놓인 모양과 맞는다. 코어 고정(m2)에서는 40회 모두 낮은 상태 하나로 모인다.
- 그래서 m1의 쌍별 차는 판정에 쓸 수 없다: 워커 CPU 표준편차가 평균의 20~35%(Opus 2.5ms 2.6~3.2%p)이고, A는 +7.5%(구간 −7.6 ~ +22.6), B는 −7.8%(구간 −18.3 ~ +2.8)로 부호도 갈린다. 6구성 모두 "걸침".

## 4. 후속 후보(백로그 — 이 PR은 고치지 않음)

1. **CPU 측정 방법(ADR D6 보강)**: 이 기계에서 `cpu_profile` 전·후 비교는 P+E 코어 고정(`start /affinity FFF`)으로 돌리고 실행마다 `iter_body` p99를 함께 적는다. 고정 없이 잰 값은 상태가 섞여 ±5%를 가를 수 없다(m1 표준편차 20~35%). `cpu_profile`에 측정 창 `iter_body` 분포 출력(이 측정의 패치)을 정식으로 넣는 것도 후보.
2. **제품 쪽 — 워커·수신 스레드가 느린 코어에 놓일 때 1.6~2배**: 코어 고정 없이 실행하면 같은 코드가 워커 CPU 1.6배(강제 Opus 2배), `iter_body` p99 2배, 콜백 p99 +50%로 갈린다. 실제 앱도 하이브리드 노트북에서 같은 일이 날 수 있다. 후보: 워커·RT 스레드에 `SetThreadSelectedCpuSets`로 LP-E 제외(효율 등급 최고·LLC 공유 코어 선호), 또는 EcoQoS/전원 조절 끄기(`SetThreadInformation(ThreadPowerThrottling)`), 스레드 우선순위·MMCSS 현 설정과의 관계 확인. 어느 스레드가 원인인지(워커·`band-net-recv`·가짜 장치 타이머)는 이 측정이 가르지 않았다 — 먼저 스레드별 코어 배치를 기록하는 측정이 필요.
3. (낮음) `iter_body` 히스토그램은 16µs 위에서 옥타브당 8칸이라 p50(수십 µs)이 칸 경계에서 크게 뛴다. 분포 비교에 쓰려면 칸을 늘리거나 합·횟수로 평균을 함께 낸다.
