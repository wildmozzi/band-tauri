# 하이브리드 CPU 코어 배치 기록 (P1-21 1단계, 2026-11-17)

- 관련: [cpu-quiet-2026-11-17.md](cpu-quiet-2026-11-17.md) 4절 2번(코어 고정 없이 워커 CPU가 1.6~2배로 갈림), 계약 [native-engine-design.md](native-engine-design.md) 4절 `corePlacement`.
- 기계: Intel Core Ultra 5 225H(P 4·E 8·LP-E 2, 논리 14), AC 전원, "균형 조정" 전원 계획. 다른 빌드·작업 없음.
- 도구: `cargo test --release -p band-engine --test cpu_profile six_peer_full_mesh_cpu -- --ignored --nocapture`. 이 PR부터 구성마다 `배치 | …` 줄을 낸다. 측정 창(12초) 동안 6엔진을 합친 워커·수신 스레드의 P / E / LP-E 표본 비율이다. 코어 고정은 하지 않았다(실제 앱과 같은 조건).

## 1. 무엇을 기록하나

- 워커: 반복마다(수면 뒤 본문 시작). 수신 스레드: 패킷을 받아 깨어날 때마다. 둘 다 `GetCurrentProcessorNumberEx`로 지금 코어를 읽어 종류별 원자 카운터를 올린다. 사용자 모드 읽기라 할당·락이 없다. 워커 반복 할당 0 시험(`engine::tests`)이 그대로 통과한다.
- 코어 종류 표는 스레드 시작 때 한 번 `GetSystemCpuSetInformation`으로 만든다. 이 기계에서는 P = LP 0·1·10·11, E = 2~9, LP-E = 12·13으로 나온다(`classify` 시험이 같은 배치를 고정한다).
- 노출: `EngineStats.corePlacement`(시작부터 누적 비율)와 진단 타임라인 샘플. 타임라인 샘플은 후속(#191 리뷰 L1·L4)에서 직전 샘플 뒤로 센 구간 원시 수 `[P, E, LP-E]`로 바뀌었다. 비Windows는 null이다.
- 해석 주의: 표본은 깨어남 가중이다(워커 반복·수신 패킷마다). 비율은 실행 시간 비율이 아니다(#191 리뷰 L2).

## 2. 결과 — 코어 고정 없음, 3회

Opus 2.5ms, 6엔진 평균 워커 CPU(%)와 측정 창의 워커·수신 배치:

| 실행 | 워커 CPU | 워커 P / E / LP-E (%) | 수신 P / E / LP-E (%) |
|---|---|---|---|
| 1 | 16.10 | 36.1 / 59.1 / 4.8 | 23.0 / 73.5 / 3.6 |
| 2 | 12.57 | 52.8 / 44.6 / 2.7 | 35.7 / 62.2 / 2.2 |
| 3 | 16.25 | 35.5 / 64.5 / 0.0 | 18.2 / 81.8 / 0.0 |

다른 구성도 같은 모양이다. 강제 Opus 2.5ms(PCM16 + 5피어 Opus):

| 실행 | 워커 CPU | 워커 P |
|---|---|---|
| 1 | 27.6 | 37% |
| 2 | 18.7 | 59% |
| 3 | 29.4 | 38% |

**읽기**

- **LP-E 비율은 0~6%로 작다.** "높은 상태"(1.3~1.6배)는 LP-E보다 **P ↔ E 비율**과 맞는다. 워커가 P에 50~60% 있으면 낮은 상태, 35% 안팎이면 높은 상태다.
- 그래서 2단계 후보 가운데 "LP-E 제외(CPU set)"만으로는 이 차이를 줄이지 못한다(이 측정 조건에서).
- 한계: 한 프로세스에 엔진 6개(스레드 30여 개)가 함께 돌아 P 코어 4개를 두고 경쟁하는 조건이다. 실제 앱(엔진 1개)의 배치는 진단 타임라인으로 따로 봐야 한다([사람]).

## 3. 2단계 시험 — 워커·수신 스레드 EcoQoS 끄기(HighQoS), 교차 3라운드

옵션: `sys::placement::set_high_qos(true)`(기본 꺼짐, 지금은 측정 빌드 `test-support`에만 있고 앱에는 연결하지 않음). 켜면 스레드 시작 때 `SetThreadInformation(ThreadPowerThrottling, ControlMask = EXECUTION_SPEED, StateMask = 0)`을 부른다. 측정은 `BAND_HIGH_QOS=1`로 켰다. 라운드마다 켬 → 끔 순서로 돌렸고, 실행 사이 쿨다운은 20초다.

6엔진 평균 워커 CPU(%), 3회 평균(괄호 안은 실행별 값):

| 구성 | HighQoS 켬 | 끔 |
|---|---|---|
| Opus 2.5ms | 13.87 (13.22·14.47·13.92) | 14.08 (11.80·17.02·13.42) |
| PCM16 2.5ms | 7.77 | 8.20 |
| PCM16 2.5ms + 5피어 Opus 강제 | 23.49 (18.06·23.57·28.83) | 26.12 (24.00·30.61·23.75) |
| Opus 5ms | 11.13 | 11.88 |
| PCM16 5ms | 5.69 | 5.97 |
| PCM16 5ms + 5피어 Opus 강제 | 21.44 | 20.10 |

Opus 2.5ms 배치(워커 P% / 수신 P%):

| HighQoS | 라운드 1 | 라운드 2 | 라운드 3 |
|---|---|---|---|
| 켬 | 58 / 61 | 58 / 40 | 66 / 56 |
| 끔 | 58 / 56 | 34 / 17 | 47 / 19 |

**판정**

- HighQoS를 켜면 P 코어 비율이 오른다. 특히 수신 스레드가 그렇다(끔 17~56% → 켬 40~61%).
- 워커 CPU 평균은 6구성 중 5개에서 조금 낮지만(−0.3 ~ −2.6%p), 실행 사이 흔들림(같은 조건에서 ±3~6%p) 안이다. **n = 3으로는 CPU 효과가 있다고 말할 수 없다.**
- 그래서 옵션만 넣고 **기본값은 바꾸지 않는다**(보고만). 앱 설정·커맨드에도 아직 연결하지 않았다.
- 다음 근거는 둘이다. ⓐ 실제 앱(엔진 1개)의 진단 타임라인 `corePlacement`. ⓑ 코어 고정 없는 교차 측정을 n ≥ 10으로(P1-21b 방법).

## 4. 후속(백로그 후보)

> 2번·3번은 2026-11-20에 교차 n = 11로 쟀다: [core-placement-2026-11-20.md](core-placement-2026-11-20.md). HighQoS + P 코어 선호를 기본 켬으로 바꿨고, 3절의 `set_high_qos`·`BAND_HIGH_QOS`는 `set_thread_policy`·`BAND_THREAD_POLICY`로 바뀌었다.

1. [사람] 하이브리드 노트북에서 실제 앱으로 10분 연주한 뒤, 진단 내보내기의 `corePlacement`(워커·수신 P/E/LP-E)와 `cpu.workerPct`를 함께 본다. 배터리와 AC 전원을 각각 본다.
2. HighQoS 옵션 효과: 코어 고정 없음 교차 n ≥ 10. 효과가 보이면 기본값 변경을 제안한다(사용자 결정).
3. (낮음) P 코어 선호 CPU set(`SetThreadSelectedCpuSets`로 P만)은 P 코어가 4개뿐인 기계에서 다른 앱과 경쟁하므로, 위 두 근거를 본 뒤에 검토한다.
