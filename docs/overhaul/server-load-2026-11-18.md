# 시그널링 서버 처리량·지연 프로파일 (발굴, 2026-11-18)

- 도구: [`server/scripts/load-signaling.ts`](../../server/scripts/load-signaling.ts) — `cd server && npx tsx scripts/load-signaling.ts [--rooms 50] [--viewers 4] [--ice 8] [--seconds 60] [--storm] [--quiet-logs] [--prof <폴더>]`
- 기계: Intel Core Ultra 5 225H(논리 14), Windows 11, Node v24.22.0. 다른 작업자 빌드가 돌던 개발 기계라 수치는 **규모 감**을 보는 값이다(같은 시나리오 반복 간 ±50%).

## 결론

1. **정상 부하는 서버에 매우 가볍다.** 방 50 × 연주자 6 + 관람자 4(연결 500)에서 다음과 같았다.
   - 이벤트 루프 사용률 1.8%, CPU 1.7%(1코어), 앱 ping 왕복 p99 0.8~1.4ms, RSS 약 80MB.
   - 관람자 10/방(연결 800)에서는 루프 3%, CPU 3.4%, ping p99 1.2~3.3ms였다.
   - 전원 동시 재접속(5~6초 안)에도 루프 사용률은 8~16%였다. 연결 상한(`maxConnections` 1000)이 먼저 닿을 규모다.
2. **메시지당 비용은 소켓 쓰기와 로그가 지배한다. JSON 직렬화가 아니다.**
   - CPU 프로파일(800 연결, 정상 + 동시 재접속) 자기 시간: `writev` 16%, `consoleCall` 7%, 서버 코드 전체 12%, ws 라이브러리 6%, GC 3%. `JSON.stringify`는 상위 25에 없다.
   - 브로드캐스트에서 수신자마다 다시 직렬화하는 것은 메시지당 0.3~1.8µs다(벤치). 이 부하에서 합쳐도 CPU 0.02% 수준이라 고치지 않았다.
3. **로그가 줄일 수 있는 가장 큰 비용이었다.**
   - 관람 연결 하나에 `[SIGNAL] ice-candidate` 줄이 양방향 16개 남아, 동시 재접속 로그의 약 80%였다.
   - 이 PR에서 ice-candidate 줄을 뺐다(offer·answer는 남김). 같은 시나리오에서 로그 줄은 입장 6950 → 3200, 동시 재접속 9650 → 5900이 됐고, `consoleCall` 자기 시간은 207 → 150ms였다.
   - 운영(fly)에서는 stdout이 로그 수집기로 가는 파이프라 비용이 더 크다.
4. **#184·#187 제한의 오탐 — 정상 부하는 오탐 없음, 다만 관람자가 몰리면 방송 담당(방장)의 ICE가 버려진다(→ 이 PR에서 고침, 아래 "고친 것").**
   - 정상 상태(ping·채팅·메트로놈·관람자 재접속)에서는 rate-limited·닫힘·room-full이 0이었다.
   - 관람자 여러 명이 한꺼번에 붙으면(서버 재시작·망 순단 뒤 재접속, 방장 엔진 재시작 뒤 전원 재offer) 방장의 일반 메시지 버킷(`msgBurst` 40, `msgPerSec` 20)이 넘친다. 방장은 관람자마다 offer 1 + ICE N개를 보내야 하기 때문이다.

| 방당 동시 관람자 | 방장 → 관람자 ICE 버려짐 — 고치기 전(ICE 8개/연결) | 고친 뒤(ICE 12개/연결) |
|---|---|---|
| 4 | 0% | 0% |
| 6 | 27% | 0% |
| 10 | 56% | 0% (방 50개 × 10명 + 동시 재접속도 0%, 오류·닫힘 0) |
| 14 | 68% | 0%¹ |

(방 10개, 입장 + 동시 재접속 두 번의 합. 관람자 쪽 answer·ICE는 각자 연결의 버킷이라 버려지지 않았다.)

¹ 6 + 14 = 정원 20이 꽉 찬 방에서는 동시 재접속 중 옛 연결이 빠지기 전에 새 연결이 들어와 `room-full`로 한 명이 튕길 수 있다(리뷰 재현 0.4%). 정원 경합이라 중계 버킷과는 별개다.

### 고친 것 (관람 중계 버킷)
- **서버**: 관람 중계(offer·answer·ice-candidate)는 일반 `msgBucket` 대신 연결의 `relayBucket`을 쓴다(`viewerRelay.takeRelayMessage`).
  - 관람자(연주자 아님)는 일반 버킷과 같은 40·20/s다. 공격 표면은 그대로다.
  - 연주자는 방 인원(rooms 멤버 수 — 익명·재개 유예 포함, 자기 제외) 1명당 +20·+2/s를 더한다(정원 20이면 420·58/s). `TokenBucket.resize`는 그 연결이 가졌던 최대 용량을 처음 넘는 몫만 토큰을 바로 더한다. 관람자가 나갔다 들어오는 출입으로는 더 받지 못한다(#215 리뷰 M1).
  - 실제로 대상에게 넘기는 양은 쌍별 메시지·바이트, 대상 수신 바이트 버킷(#184·#187)이 그대로 묶는다. 관련 시험은 그대로 통과한다.
  - 중계는 처리 대기 상한(`MAX_PENDING_MESSAGES` 100)에 세지 않는다. 버킷만 고치자 한 번 읽기에 182개가 들어와 1008로 끊겼기 때문이다. 대신 중계 전용 상한을 둔다(#215 리뷰 H1). 리뷰 탐침(체인 정지 + 64KB 중계)에서는 메모리가 +258MB였다.
    - 원문 크기 20KB(`MAX_RELAY_MESSAGE_BYTES`)
    - 연결당 대기 500개·1MB(`MAX_PENDING_RELAY_*`)
    - 넘으면 끊지 않고 버리고 속도 제한 버림으로 센다. 순서는 같은 체인에서 지킨다.
- **클라이언트**(`mixBridge`): `rate-limited`(rejectedType offer·ice-candidate)를 받으면 다음처럼 한다.
  - 10초 동안 중계를 약 15/s로 줄 세워 보낸다(옛 서버 일반 버킷 20/s보다 여유).
  - 늦춰 보내기 창마다 한 번, offer를 **실제로 보낸 지** 3초가 지났는데 answer가 없는 관람자에게만 offer를 다시 보낸다. 줄에 남은 offer는 다시 만들지 않고, 창 안에서 알림이 거듭 와도 반복하지 않는다(#215 리뷰 M2). 나머지는 연결 시간 초과(15초)와 주기 sync가 시간 기반으로 진행한다.
  - 새 서버에서는 오지 않는다. 옛 서버나 다른 한도에 대한 방어다.
  - ICE 묶음 전송은 프로토콜(후보 1개/메시지)을 바꿔야 해서 하지 않았다.

## 트래픽 모양

실제 클라이언트 코드를 기준으로 잡았다. 연주 오디오·통계·레벨은 UDP(엔진 간)와 WebRTC(관람)로 가므로 시그널링 서버를 지나지 않는다. 그래서 "통계·레벨" 메시지는 서버 부하에 없다.

| 종류 | 빈도(하네스) | 근거 |
|---|---|---|
| 앱 `ping` | 연결마다 15초 | `useSignaling` `IDLE_PING_MS`(수신이 있으면 미뤄지므로 상한) |
| 채팅 | 연주자 평균 30초, 관람자 평균 120초 | 방 전체 브로드캐스트 |
| 메트로놈 | 방장 평균 20초 | 연주자에게 브로드캐스트 |
| 관람자 재접속 | 평균 10분 | 입장 → 방장 offer + ICE, 관람자 answer + ICE |
| 입장 | 연주자: auth·join·start-performing·native-descriptor | `performSession` |
| relay-token-request | 생략 | 토큰 수명(분 단위)마다 1회라 무시할 양 |

- **이벤트 루프 지연(`monitorEventLoopDelay`)**: Windows 기본 타이머 해상도(15.6ms) 때문에 빈 서버에서도 p99가 약 16ms로 나온다. 그래서 판정에는 루프 사용률(ELU)과 앱 ping 왕복을 썼다. 동시 재접속 구간의 최대 지연은 21~58ms였다. Linux(fly)에서 재야 ELD 절대값이 의미 있다.
- **로그 끔(`--quiet-logs`) 비교**는 같은 구간의 다른 작업 잡음(ping p99가 한때 50ms)이 커서 차이를 가를 수 없었다. 로그 비용은 CPU 프로파일 자기 시간으로 봤다.
- 연결당 메모리: 500 → 800 연결에 RSS +10MB 안팎이다(연결당 약 30KB 미만).
