# 실장비 합주 테스트 세션 가이드

PC 2대로 **한 번의 테스트 세션**에서 백로그의 **[사람]** 확인 항목을 최대한 많이 끝내기 위한 가이드다. 버튼 이름과 화면 문구는 `develop` 코드(2026-11-20, `1104803`)에서 그대로 옮겼다. 처음 판(#55, overhaul `1b2b095`)에서 바뀐 곳은 PR #242 본문 "고친 낡은 내용"에 있다.

다른 문서와의 경계(같은 내용을 두 곳에 쓰지 않는다):
- 하드웨어 루프백·에코 측정의 단계와 결과 표 읽는 법은 [MEASURE.md](MEASURE.md)가 원본이다. 이 문서는 "세션 중 언제, 몇 번, 무엇을 기록하나"만 적는다.
- 설치본(릴리스)·서명·서버 배포 규칙은 [RELEASE.md](RELEASE.md), 운영 첫 반영 순서는 [DEPLOY-CUTOVER.md](DEPLOY-CUTOVER.md)가 원본이다.

- **1부: 같은 LAN**(약 90분). 같은 공유기에 두 PC를 연결한다.
- **2부: 다른 네트워크**(약 40분). PC B를 휴대폰 LTE 핫스팟이나 다른 집 인터넷으로 옮긴다.
- 결과는 맨 아래 **8절 결과 기록표**에 적는다. 진단 zip 파일과 측정 결과 텍스트도 함께 보낸다.

표기 규칙

## 0. 먼저 알아 둘 것 — 서버와 DB

| 항목 | 현재 상태 | 이 세션에서 하는 일 |
|---|---|---|
| 시그널링 서버 | 운영(`band-server.fly.dev`)은 2026-11-20 컷오버(P3-21)로 `develop`과 같은 세대가 됐다(`main` ← #231·#235). 하지만 **데스크톱 설치본 릴리스는 아직 없고**(P3-21 남은 일), 개발 실행 앱은 `.env`의 `auto` 설정으로 로컬 서버에 붙는다. | **PC A에서 로컬 서버**를 띄우고 두 PC가 모두 그 서버에 붙는다. 서버 로그를 직접 보고, 2부에서 로컬 릴레이를 붙일 수 있다. |
| UDP 릴레이 | 운영에 배포되지 않았다(P1-4 — fly 전용 IPv4가 유료라 보류). | 2부에서만, PC A에서 로컬 릴레이를 띄운다(4.2절, 선택). |
| client `.env` | `VITE_SIGNALING_URL=auto`, `VITE_API_URL=auto`(`client/.env.example`). 개발 실행에서 `auto`는 앱 자신의 개발 서버(Vite, `https://localhost:5173/__band_server/…`)를 거쳐 서버에 붙는다. Vite가 대상 서버의 인증서 유무에 맞춰 `ws://`/`wss://`로 넘긴다. | **아무것도 바꾸지 않는다.** `.env` 그대로 실행한다. 다른 PC의 서버는 오디오 설정 창의 **개발 서버** 칸으로 고른다(2.3절). |
| DB·로그인 | client와 server의 `.env`가 모두 **운영 Supabase 프로젝트**를 가리킨다. 개발용 DB(P3-11)는 아직 없다. | 운영 DB에 아래 쓰기가 생긴다. |

**운영 DB에 생기는 쓰기**(알고 진행할 것)
- 테스트 계정 가입(Supabase Auth + `profiles` 행). 계정이 없으면 2개를 만든다. 가입 화면은 **이름·닉네임·이메일·생년월일·비밀번호**가 필수이고 이 값이 운영 DB에 저장된다 — 실제 개인정보 대신 테스트용 값(예: 이름 `테스트A`, 받을 수 있는 테스트 메일 주소)을 넣는다. 가입 화면에는 "회원가입 후 이메일 확인이 필요합니다."라고 나오지만, 운영 Supabase는 이메일 인증이 꺼져 있어 가입하면 바로 로그인된다(P3-21 기록, 2026-11-20).
- 테스트 방 생성(`rooms` 행). 방은 로컬 서버의 `POST /api/rooms`로 만들어진다. 끝나면 방 정보 창에서 삭제한다(4.5절).
- 로컬 서버는 운영 DB의 주 서버가 아니라서(#243) 다음을 **하지 않는다**. 운영 서버(fly, `NODE_ENV=production`)만 한다.
  - 시작 때 모든 방 참가자 수 0 초기화
  - 입장·퇴장 때의 참가자 수 갱신 — 그래서 테스트하는 동안 방 목록의 인원은 **0으로 보인다**(정상)
  - 정기 작업: 미확정 결제 재조정(시작 10초 뒤·5분마다), 만료 구독 처리·만료 주문 정리(1시간마다), 미검증 업로드 파일 삭제(post-images·avatars, 매시), 만료 음원분리 결과 파일·행 삭제(매일 03:00), 고아 게시글 이미지 정리(03:30)
- 로컬 서버는 켜질 때 `[DB] Supabase client initialized - participant sync disabled (not the primary server)`와 `[MAINT] 전역 유지보수(참가자 수 초기화·갱신, 정리·구독·주문 주기 작업) 건너뜀: 개발 모드(NODE_ENV=development) — 켜려면 RUN_MAINTENANCE_JOBS=true`를 남긴다. `server.env`에 `RUN_MAINTENANCE_JOBS`(`true|false|1|0`)를 켜는 값으로 넣지 않는다(운영 서버와 겹쳐 돈다).

⚠️ **서버를 띄우는 모든 단계**(2.2 `npm run dev:tauri`, 3.3 `npm run dev:tauri:asio`, 3.7·4.2의 `npm run dev:server`·재실행)에서 서버 터미널에 위 `[MAINT] … 건너뜀` 줄이 보이는지 확인한다. 이 줄 대신 `[MAINT] 전역 유지보수 실행 (…)`·`participant sync enabled`·`[DB] All room participants reset to 0`이 보이면 #243 이전 코드이거나 `RUN_MAINTENANCE_JOBS=true`(또는 `1`)가 켜져 있는 것이다. 그때는 켜질 때마다 운영의 **모든 방 참가자 수가 0이 되고**, 입·퇴장 때 로컬 인원으로 방 인원을 덮어쓰며, 위 정기 작업(결제 재조정·주문 정리·파일 삭제)이 운영 서버와 겹쳐 돈다 — 바로 끄고 `git pull` 또는 `server\.env`를 고친다. 2026-11-20부터 운영 서버가 같은 DB를 쓰므로, **누군가 운영에서 합주·관람 중이면 로컬 서버를 켜지 않는다**([HUMAN-CHECKS.md](HUMAN-CHECKS.md)와 같은 규칙).

스키마 변경이나 마이그레이션은 없다.

## 2. 설치와 실행

### 2.1 PC A (서버 + 방장 앱)

PowerShell에서 한 줄씩 실행한다. 리포 폴더는 예를 들어 `C:\dev\devdev\band-tauri`다.

```powershell
cd C:\dev\devdev\band-tauri
git status                 # "nothing to commit, working tree clean"인지 확인. 작업 중인 변경이 있으면 멈추고 정리한다
git fetch origin
git switch develop
git pull
npm install
```

`develop`은 자동 병합되는 개발 브랜치다. 운영과 같은 코드로 시험하려면 `develop` 대신 `main`을 고른다(2026-11-20 기준 `main`은 `develop`보다 웹·스크립트 커밋 몇 개가 뒤이고 엔진 코드는 같다). 어느 쪽인지 기록표의 "앱 커밋"에 적는다.

`server\.env`와 `client\.env`가 있는지 확인한다. 둘 다 이미 있어야 한다. 값은 바꾸지 않는다.

### 2.2 PC A 실행

```powershell
cd C:\dev\devdev\band-tauri
npm run dev:tauri
```

- 환경 변수는 따로 주지 않는다. 예전 가이드대로 이 창에서 `$env:VITE_SIGNALING_URL`/`$env:VITE_API_URL`을 넣은 적이 있으면 **PowerShell 창을 새로 연다**(직접 지정한 주소는 `.env`보다 우선하고 개발 서버 프록시를 건너뛴다).
- 터미널에 `HTTP + WS server listening on port 8080`이 보이고 잠시 뒤 앱 창이 뜬다. 그 위에 `[MAINT] … 건너뜀` 줄이 있는지 확인한다(없으면 0절 ⚠️대로 바로 끈다).
- **Windows 보안 경고(방화벽)** 창이 `node.exe`와 `band.exe`에 대해 각각 뜨면, **개인 네트워크와 공용 네트워크를 모두 체크**하고 **액세스 허용**을 누른다. 거부하면 PC B가 서버에 붙지 못하거나 오디오 직접 연결이 실패한다(7절).
- PC A의 LAN IP를 확인한다: `ipconfig` → 사용 중인 어댑터의 `IPv4 주소`(예: `192.168.0.10`). 이 값을 **A_IP**라고 부른다.
- 8080이 아닌 포트로 서버를 띄우려면 `server\.env`의 `PORT`를 바꾼다. 같은 PC의 개발 서버는 이 값을 읽어 자동으로 허용한다. 다른 PC(PC B)에서는 앱을 실행하기 전에 같은 창에서 `$env:BAND_DEV_PROXY_PORTS = '<포트>'`를 넣고(쉼표로 여러 개), 2.3절의 **개발 서버** 칸에 `<A_IP>:<포트>`를 넣는다. PC A도 **개발 서버** 칸에 `localhost:<포트>`를 넣는다(기본값은 `localhost:8080`).

### 2.3 PC B (손님 앱)

PC B는 PC A의 서버를 써야 한다. PC B 앱의 개발 서버(Vite)가 **설정 화면의 "개발 서버" 주소**로 요청을 넘기므로, 그 칸에 A_IP만 넣으면 된다. 포트 프록시(netsh)나 환경 변수는 필요 없다.

1. 코드 받기:
   ```powershell
   git clone https://github.com/wildmozzi/band-tauri.git
   cd band-tauri
   git switch develop   # PC A와 같은 브랜치·커밋
   npm install
   ```
2. PC A의 `client\.env`를 USB 등으로 복사해 PC B의 `band-tauri\client\.env`에 둔다. Supabase 주소와 공개용 anon 키만 들어 있다. `server\.env`(서비스 키)는 **복사하지 않는다**. PC B에서는 서버를 띄우지 않는다.
3. 확인: PC B의 브라우저에서 `http://<A_IP>:8080/health`를 열면 응답이 와야 한다. 안 오면 PC A 방화벽(2.2절, `node.exe` 허용 = TCP 8080)과 A_IP를 확인한다.
4. 앱 실행(일반 PowerShell). PC B에는 `server\.env`가 없으므로 서버 없이 앱만 띄우는 `npm run tauri:dev`를 쓴다(`server\.env`가 있는 PC라면 `npm run dev:tauri`도 된다 — 앱은 개발 서버 칸에 넣은 대상만 쓴다).
   ```powershell
   cd band-tauri
   npm run tauri:dev
   ```
5. `band.exe` 방화벽 경고가 뜨면 개인·공용 모두 허용한다.
6. **개발 서버 주소 넣기**: 상단 🎛️(오디오 설정) 버튼을 눌러 뜨는 창의 맨 아래 **개발 서버 (개발 실행 전용)** 칸에서(`/settings/audio` 페이지에도 같은 칸이 있다):
   - **개발 서버 주소** 입력란에 `<A_IP>:8080`(예: `192.168.0.10:8080`)을 넣고 **저장 후 새로고침**을 누른다.
   - 새로고침 뒤 `지금 연결: http://192.168.0.10:8080 · 시그널링 wss://localhost:5173/__band_server/http/192.168.0.10:8080`처럼 보이면 된다.
   - `localhost 또는 사설 IP(10.x, 172.16~31.x, 192.168.x)와 포트만 입력하세요.` 가 뜨면 입력값을 고친다. 도메인과 공인 IP는 받지 않는다.
   - PC A 서버가 인증서(`server\certs`)로 `wss://`를 쓰면 `https://<A_IP>:8080`처럼 앞에 `https://`를 붙인다.
   - 주소는 이 PC에 저장되어 앱을 다시 켜도 유지된다. 화면 위쪽 메뉴의 **합주실**로 돌아간다.

테스트가 끝나면 PC B에서 같은 페이지의 **기본값**을 눌러 되돌리고(`localhost:8080`), 두 PC 모두 앱과 개발 서버를 끈다(`Ctrl+C`). 개발 서버는 LAN에 열려 있어, 켜 둔 동안 같은 LAN의 기기가 이 PC를 거쳐 사설망의 서버 포트에 닿을 수 있다.

### 2.4 로그인과 오디오 설정 (두 PC 각각)

1. 앱 위쪽 메뉴의 **로그인**에서 각자 다른 계정으로 로그인한다.
2. 위쪽 오른쪽의 **🎛️(오디오 설정)** 을 누른다.
3. **프리셋**은 **초저지연**(버퍼 64 · 2.5ms · PCM16 · 모노 (LAN/유선 권장)), **균형**(버퍼 128 · 5ms · Opus · 모노), **안정**(버퍼 256 · 10ms · Opus · 스테레오 (불안정한 회선)), **사용자 정의** 넷이다. **균형**을 고른다. 처음 연결을 확인하기에 가장 무난하다. 1부 후반에 **초저지연**으로도 한 번 잰다.
4. **입력 / 출력**: 드라이버를 **WASAPI 독점**으로 고르고, 장치에는 헤드폰과 마이크(또는 인터페이스)를 고른다. 독점이 실패하면 **WASAPI 공유**로 바꾸고 기록표에 적는다. 기본 실행(`npm run dev:tauri`/`tauri:dev`)에는 ASIO가 들어 있지 않아 드라이버 목록에 **ASIO (이 배포본에 없음)** 으로 보이고 고를 수 없다. ASIO는 3.3절의 ASIO 빌드에서만 쓴다.
5. **테스트 모니터 → 테스트 시작**: 마이크에 말하면 **입력 레벨**이 움직이고 헤드폰에서 내 소리가 들려야 한다. **로컬 처리 지연**, **장치**(kHz · 버퍼), **리샘플러**, **xrun** 값을 기록표에 적는다. 확인했으면 **테스트 중 (끄기)** 를 누른다. 합주 중에는 "합주 중에는 테스트할 수 없습니다."가 뜨고 버튼이 눌리지 않는다.
6. 아래쪽에 **설정은 자동으로 저장됩니다**가 보이면 **완료**를 누른다.

## 3. 1부 — 같은 LAN

### 3.1 방 만들기와 입장 (P2-6, P3-4a)

**PC A(방장)**
1. 메뉴 **합주실** → **+ 새 합주실 만들기**.
2. **방 제목 \***에 `[TEST] 실장비 테스트`를 입력한다. 폼의 기본값은 **자유 참여 · 공개 · 비밀번호 없음**이다. **참여 방식** 스위치를 꺼서 **자유 참여 → 승인 필요**로 바꾼다(승인 화면도 같이 확인). **공개 여부** 스위치를 꺼서 **공개 → 비공개**로 바꾼다(공개로 두면 `[TEST]` 방이 운영 웹 방 목록에도 보인다). **비밀번호**는 **비밀번호 없음** 그대로 둔다. 맨 아래 **합주실 만들기**를 누른다.
3. 만든 뒤 합주실 화면 위쪽의 **ℹ️ 정보** → **#️⃣ 방 코드 복사**를 누르고, 메신저 등으로 PC B에 보낸다. **🔗 초대 링크 복사**는 쓰지 않는다: `client\.env`의 `VITE_PUBLIC_WEB_URL`이 비어 있으면 개발 실행의 링크는 `https://localhost:5173/rooms/<방 코드>`라 다른 PC에서 열리지 않고, 값이 있으면 그 웹 주소(관람 웹)로 연결된다.
4. 왼쪽 연주자 패널(**🎸 연주자**)의 **🎤 연주 참여하기** → "연주할 악기를 선택하세요" 창에서 악기를 고른다. 오디오 엔진이 시작된다(**⏳ 오디오 엔진 시작 중...**).

**PC B(손님)**
1. **합주실** → **방 코드 또는 초대 링크로 입장** 칸에 받은 코드를 넣고 **입장**을 누른다.
2. "이 방은 방장 승인이 필요합니다" 안내를 확인하고 **🎤 연주 참여하기** → 악기를 고르면 **⏳ 방장 승인 대기 중...** 이 뜬다(아래에 "승인되면 오디오 엔진이 자동으로 시작됩니다.").
3. PC A의 연주자 패널에 숫자 배지가 붙은 **연주 참여 요청** 알림이 뜬다. 눌러서 열리는 요청 창에서 **✓ 승인**을 누른다. PC B에는 **✅ 승인되었습니다!** 가 뜨고 엔진이 자동으로 켜진다. 자동으로 안 켜지면(그 아래 "엔진을 자동으로 시작하지 못했습니다. 설정을 확인한 뒤 다시 시도하세요.") **🎤 연주 시작하기**를 누른다.
4. (선택, P2-9) **관람자로 내리기**: PC A의 연주자 목록에서 PC B 행의 **관람자로 내리기** → "…님의 연주를 멈추고 관람자로 내릴까요?" → **내리기**. PC B에 "방장이 나를 관람자로 전환했습니다. 다시 연주하려면 "연주 참여하기"를 누르세요(승인제 방은 방장 승인이 필요합니다)."가 뜨고 PC A에서 PC B 소리가 끊기는지 본다. 다시 1~3번으로 참여한다.

확인: 비공개 방이 목록에 보이지 않는다. 방 코드로 입장이 된다. 승인 요청과 승인이 동작한다. 화면이 깨지지 않는다(P3-8a).

입장 뒤 **3초 안에** 상대 소리가 들리는지 본다(GOAL 3절). 서로 말하거나 연주해 본다.

합주실 화면은 왼쪽 연주자 패널, **가운데 🎚️ 개인 믹서**, 오른쪽 채팅이다. 가운데 개인 믹서에서 읽는 값:

경로 표시: **LAN** = 같은 공유기 안 직접 연결, **인터넷** = 공인 주소로 직접 연결, **릴레이** = 서버 경유(옆에 "서버 경유 — 지연 증가").

**은닉률과 목표 버퍼**: 합주 중에 🎛️ 오디오 설정을 열면 **지터 버퍼** 칸에 피어별로 `버퍼 6.0ms / 목표 6.0ms · 은닉 0.0% · 보정 1%`가 보인다. 은닉은 최근 5초 동안 끊긴 소리를 메운 비율이다. 목표는 GOAL 2절 기준 ≤ 1.5%다. 이 창을 열어 두어도 합주는 계속된다.

백엔드·우선순위·QoS 정보는 진단 zip의 `logs/*.log`에도 남는다(`스레드 band-worker: MMCSS "Pro Audio" 등록`, `스레드 band-net-recv: …`).

**아직 화면에 없는 값**(메트로놈 동기 3.5절, 릴레이 4절, 송신 큐, 피어별 송신 코덱): 개발자 도구(앱 화면에서 마우스 오른쪽 → **검사**(또는 `Ctrl+Shift+I`) → **Console** 탭, 처음 붙여 넣을 때 경고가 뜨면 `allow pasting` 입력 후 다시)에 아래를 붙여 넣는다.

```js
const s = await window.__TAURI__.core.invoke('engine_stats'); JSON.stringify({ sendQueue: s.sendQueue, relay: s.relay, metronome: s.metronome, peers: s.peers.map(p => ({ state: p.state, path: p.path, txCodec: p.txCodec, txCodecAuto: p.txCodecAuto })) }, null, 1)
```

- `sendQueue.p99Ms`: 송신 큐 지연. 1ms 미만이면 정상이다.
- `metronome`, `relay`, `txCodec`은 3.5절·4절에서 읽는다.

**기록**: 1분 동안 지켜본 뒤 RTT, 버퍼, 목표, 은닉, 손실, 처리 지연, xrun, 백엔드, 우선순위 줄(+ 1ms 타이머), QoS 줄, 첫 소리 줄을 기록표에 적는다. 프리셋 **균형**과 **초저지연** 각각 적는다. 프리셋을 바꾸면 "합주 중 바꾼 설정은 연주를 다시 시작하면 적용"되므로 **👀 관람자로 전환** → **🎤 연주 참여하기**로 엔진을 다시 켠다.

### 3.3 (선택) 하드웨어 루프백 — ASIO·Scarlett (P1-1a, P1-0, P1-11)

오디오 인터페이스와 케이블이 있을 때만 한다. 루프백은 **합주 중에는 잴 수 없다**. 측정할 PC에서 먼저 **👀 관람자로 전환**을 누른다.

- 절차(인터페이스 설정·케이블·측정·결과 읽기)는 [MEASURE.md](MEASURE.md) 1~4절이 원본이다. 앱에서는 🎛️ 오디오 설정 → **테스트 모니터** 아래 **지연 측정 (하드웨어 루프백)** 절 → 반복 8회 → **측정 실행** → **결과 복사** 또는 **텍스트로 저장**(`loopback-….txt`).
- ASIO를 쓰려면 ASIO 피처로 빌드한 앱이어야 한다(기본 실행에는 ASIO가 없다, 2.4절). PC A에서 2.2절 대신 아래처럼 실행한다. 이 명령도 서버와 앱을 함께 띄운다. SDK 준비와 `CPAL_ASIO_DIR`의 뜻은 [README](../README.md) "요구 사항"에 있다.
  ```powershell
  $env:CPAL_ASIO_DIR = 'C:\경로\asiosdk_2.3.4'   # ASIO SDK 폴더
  npm run dev:tauri:asio
  ```
  서버가 다시 켜지므로 터미널의 `[MAINT] … 건너뜀` 줄을 다시 확인한다(0절 ⚠️).
  PC B에서 ASIO를 쓰려면 `npm run tauri:dev:asio`(서버 없이 앱만)를 쓴다.
- 버퍼 32 / 64 / 128(ASIO)과 WASAPI 독점 1회의 결과에서 "백로그 기록" 줄을 기록표에 붙인다.
- P1-0: 같은 인터페이스를 **WASAPI 독점**으로 열고 합주하면서 청취한다(지직거림이 없어야 한다). 합주 중 **USB를 뽑았다 꽂았을 때** 앱이 어떻게 되는지 적는다. 엔진은 장치를 잃으면 합주를 끝내지 않고 엔진만 다시 연다. 합주실 화면 위쪽 띠에 아래 문구 중 무엇이 떴는지 그대로 적는다.
  - "오디오 장치가 바뀌어(헤드폰 연결·분리, 샘플레이트 변경 등) 엔진을 다시 시작하는 중입니다…"
  - "오디오 장치가 바뀌어 엔진을 다시 시작했습니다. 합주는 계속됩니다."
  - "쓰던 오디오 장치를 열 수 없어 기본 장치로 다시 시작했습니다. 오디오 설정을 확인하세요."
  - "오디오 장치를 다시 열지 못해 연주를 중단했습니다. …" / "오디오 장치가 계속 바뀌어 연주를 중단했습니다. …"

### 3.4 에코 측정 — 네트워크 포함 지연 (P1-7, P1-1a)

측정 단계와 결과 표 읽는 법(판정, 튄 값 제외, 잔차)은 [MEASURE.md](MEASURE.md) 5절이 원본이다. 이 세션에서는:

1. PC A: 연주자 목록의 PC B 행에서 **📏**(연결됨 상태여야 눌린다) → **측정 시작**. PC B 화면에 "○○님이 에코 측정을 요청했습니다. 허용하면 …"가 뜨면 30초 안에 **허용**을 누른다. 측정 중 PC B에는 "🔁 ○○님의 에코 측정에 응답 중(측정이 끝나면 자동으로 멈춥니다)"이 보인다.
2. PC A 결과 창에서 **텍스트로 저장**(`echo-….txt`)을 누른다. 같은 조건에서 **3번** 재고 **입→귀 추정**의 중앙값을 기록표에 적는다. 텍스트 끝의 `백로그 기록:` 줄도 붙인다.
   - **불안정**이면 잠시 뒤 다시 잰다. 3번 중 2번 이상 불안정이면 그 판정 줄(흩어짐 Xms 또는 클릭 검출 개수)과 경로를 기록표에 적는다.
3. 방향을 바꿔(PC B가 PC A를 측정) 한 번 더 잰다.

판정 기준(GOAL 1절): 같은 도시(RTT ≤ 10ms) 입→귀 ≤ 25ms. 같은 LAN이면 이보다 훨씬 작아야 한다. 잔차가 5ms를 넘으면 메모한다(MEASURE.md 5절).

### 3.5 공유 메트로놈 (P2-3, P2-3a, P2-3c)

권장 드라이버는 **WASAPI 독점**(또는 ASIO)이다. 이 드라이버들은 출력 지연을 보고해서 클릭 시각이 보정된다. WASAPI 공유(cpal)는 보고가 없어, 3.3절 루프백 측정(정상 판정)을 해 두어야 보정된다.

1. PC A(방장): 연주자 패널의 **메트로놈** 칸에서 **BPM** `100`, **박자** `4/4` → **시작**. 상태가 `100 BPM · 4박`으로 바뀐다.
2. PC B: 상태가 **방장 시계 맞추는 중…** 이었다가 1~2초 안에 `100 BPM · 4박`이 되고 클릭이 들린다. 5초가 지나면 상태가 **방장과 시계를 맞추지 못했습니다(연결·앱 버전 확인)** 로 바뀐다. 이 문구가 뜨면 실패로 기록한다.
3. 강박(마디 첫 박)은 높은 소리, 나머지는 낮은 소리인지 확인한다.
4. **같은 박에 들리는지 확인**(둘 중 하나):
   - **귀로**: 두 헤드폰을 한쪽 귀에 하나씩 대고 듣는다. 클릭이 "딱" 한 번으로 들리면 차이가 약 5ms보다 작다. "따닥"처럼 두 번 들리면 어긋난 것이다.
   - **녹음으로**(정량): 두 헤드폰을 휴대폰 마이크에서 **같은 거리**(1cm 이내 차이)에 맞대어 놓고 30초 녹음한다. Audacity에서 파형을 확대해 같은 박의 두 클릭 시작점 차이(ms)를 5박 이상 잰다. 목표는 ≤ 2ms다. 한쪽 클릭을 잠깐 🔇로 꺼서 어느 클릭이 어느 PC인지 확인한다.
5. 개발자 도구 명령(3.2절)의 `metronome`에서 `synced: true`, `clockRttMs`, `clockOffsetMs`, `outputLatencyMs`(null이면 보정 안 됨), `lateClicks`, `skippedClicks`를 적는다.
6. 방장이 **BPM**을 `120`으로 바꾸고 **적용** → PC B도 따라 바뀌는지 본다. **정지** → 양쪽 클릭이 멈추는지 본다.
7. **클릭 볼륨 영속**(P2-3a): PC B에서 클릭 볼륨 슬라이더를 30% 정도로 내리고 🔔를 눌러 🔇로 만든다. 방에서 나갔다 들어오고, 앱을 껐다 켠다. 볼륨과 뮤트가 그대로인지 본다. 계정별로 저장된다(`band.metronomeGain.<사용자>`).
8. **출력 지연 보정 표시**(P2-3c): 메트로놈 칸 아래 줄이 `출력 지연 보정: 드라이버 보고 …ms` / `루프백 측정 …ms` / `없음`인지 적는다(5번 `outputLatencySource`와 같아야 한다). `없음`이면 **지연 측정 열기** → 오디오 설정의 지연 측정 절이 열리는지 본다. 연주를 멈추고 3.3절 측정(정상 판정)을 하면 결과에 **메트로놈 클릭 보정에 적용됨**이 뜬다. 같은 장치·버퍼로 **앱을 껐다 켜고** 다시 연주에 들어가 이 줄이 `루프백 측정 …ms`(앱을 끄기 전과 같은 값)인지 확인한다. 장치나 버퍼를 바꾸면 `없음`으로 돌아가야 한다.

### 3.6 합주 녹음 (P2-4)

1. 메트로놈을 켠 상태로 둔다. 녹음에 클릭이 **들어가지 않아야** 한다(녹음 칸 아래 안내: "내 입력과 연주자별 소리를 따로 WAV·FLAC으로 저장합니다(같은 타임라인, 메트로놈 클릭 제외). 끊김(은닉·버림) 구간은 세션 폴더의 markers.json에 남습니다.").
2. 개인 믹서 아래 녹음 칸에서 📁 저장 폴더를 확인한다. 기본값은 `음악\Band Recordings`다. **폴더 변경**으로 다른 폴더를 고를 수 있다. 엔진이 꺼져 있으면 녹음 버튼이 눌리지 않는다(마우스를 올리면 "엔진이 켜진 뒤에 녹음할 수 있습니다").
3. 파일 형식 선택은 **WAV 24비트**(기본) 그대로 둔다(그 밖에 **FLAC**, **WAV 32비트 float**). **믹스도 저장**을 체크하고 **⏺️ 멀티트랙 녹음**을 누른다. `🔴 0:12 · 4.1 MB · 3트랙`처럼 시간·용량·트랙 수가 올라간다.
4. 서로 연주를 1~2분 한다. 중간에 PC B가 잠깐 **👀 관람자로 전환** → 다시 **연주 참여하기**를 하면 같은 트랙에 이어 써지는지도 볼 수 있다.
5. **⏹️ 녹음 정지** → `저장됨 · 3트랙 · 1:30 · 45.0 MB`로 시작하는 안내가 뜬다. 끊김 구간이 있었으면 뒤에 ` · 끊김 구간 N곳(markers.json)`이 붙는다(N을 적는다). "디스크가 느려 …ms를 무음으로 채웠습니다", "저장 실패: …", "일부 저장 실패: …" 경고가 떴다면 그대로 기록한다. 엔진이 먼저 꺼지면 "녹음이 끝났습니다(엔진 정지) · <폴더>"가 뜬다.
6. 폴더 확인: `YYYY-MM-DD HH.MM.SS [TEST] 실장비 테스트` 폴더 안에 `00-mix.wav`, `01-나.wav`, `02-<상대 닉네임>.wav`, `session.json`, `markers.json`(끊김 구간 목록 — 없으면 트랙마다 빈 목록)이 있어야 한다.
7. DAW나 Audacity에 모든 트랙을 0초 위치에 올린다.
   - 트랙 길이가 모두 같은지 본다.
   - 상대 트랙이 내 트랙과 들은 그대로 맞물리는지 본다(내가 합주 중에 들은 타이밍 = 녹음 타이밍).
   - 늦게 들어온 연주자 트랙은 앞부분이 무음인지 본다.
   - **메트로놈 클릭이 어느 트랙에도 없는지** 청취한다.
8. (선택) 1시간 녹음: 합주를 1시간 이어 가며 녹음하고, 정지 후 경고가 없는지와 xrun이 늘지 않았는지 본다. 4GB가 넘는 RF64 파일 열기는 3시간 이상 걸리므로 이번 세션에서는 하지 않는다.

### 3.7 CPU 기록 (P1-10)

- 합주 중 **나 (모니터)** 채널의 `CPU 워커 x% · 콜백 y% (p99 zµs)`를 기록한다. 마우스를 올리면 상세가 보인다: `워커 스레드 CPU`, `오디오 콜백 사용률`, `출력 콜백 p50/p99/최대`, `p99 / 장치 주기`, `입력 콜백 최대`, `창: …초, 콜백 …회`. 워커 값은 "오디오 워커 스레드만입니다. 앱 전체 CPU가 아닙니다".
- 같은 시각 **작업 관리자 → 세부 정보**에서 `band.exe`의 CPU %를 적는다.
- 주의: `npm run dev:tauri`/`tauri:dev`는 **디버그 빌드**라 암호화·Opus가 최적화되지 않아 CPU가 실제보다 크게 나온다. 정확히 재려면 앱을 끄고 `cd client; npx tauri dev --release`로 다시 실행해서 잰다(첫 빌드 수 분, PC A는 서버를 다른 창에서 `npm run dev:server`로 — 서버를 다시 띄울 때마다 `[MAINT] … 건너뜀` 줄 확인, 0절 ⚠️). 릴리스 실행에서는 개발자 도구가 열리지 않는다(`devtools`는 기본 꺼진 Cargo 피처). 진단 줄은 화면에 그대로 보인다.
- 2인 기준 값이다. GOAL의 6인 판정은 2대로는 할 수 없으니 "2인"이라고 적는다.

### 3.10 진단 내보내기 (P2-5)

1. 합주 중 개인 믹서 제목 줄(**🎚️ 개인 믹서** 옆)의 **🩺 진단 내보내기** 를 누른다(🎛️ 오디오 설정의 **진단 내보내기** 절에도 같은 버튼이 있다).
2. 저장 대화상자가 앱 창 위에 뜬다. 이름은 그대로 두고 저장한다. 화면에 **저장했습니다: <경로> — 이 파일을 개발자에게 보내 주세요.** 가 뜬다.
3. **연속 클릭**: 버튼을 빠르게 두 번 누른다. 대화상자가 두 개 뜨지 않아야 한다(버튼이 **내보내는 중…** 으로 바뀌어 막힌다). **취소**를 누르면 **저장을 취소했습니다.** 가 뜬다.
4. zip을 열어 확인한다:
   - 파일 이름은 `band-diag-YYYYMMDD-HHMMSS.zip`(UTC 시각)이다. 안에 `README.txt`, `meta.json`, `engine.json`, `timeline.jsonl`, `logs\*.log`가 있다.
   - `timeline.jsonl`: 한 줄이 1초다. `peers` 안에 `path`, `bufferMs`, `concealed`, `txCodec`, `connectMs`, `firstAudioMs`가 있다. 연결 시도·결과(단계 `connect`/`reconnect`/`recover`/`switch` × 결과 `lan`/`public`/`relay`/`failed`/`aborted`)가 생긴 초의 줄에는 `conn` 목록이 붙는다(P1-18).
   - **마스킹 확인**: 메모장으로 `logs\*.log`와 `engine.json`을 열고 `Ctrl+F`로 찾는다.
     - IP는 `192.168.x.x`처럼 앞 두 자리만 남아야 한다. 내 IP 전체(예: `192.168.0.10`)가 보이면 안 된다.
     - 내 **이메일**, `eyJ`로 시작하는 토큰(JWT)이 없어야 한다.
     - `C:\Users\<내 이름>`이 `C:\Users\<user>`로 바뀌어 있어야 한다.
     - 피어 id는 `id-` + 8자리로 바뀌어 있다.
     - 오디오 장치 이름은 진단에 필요해서 그대로 남는다(정상).
5. 각 단계(1부 끝, 2부 끝)마다 두 PC에서 모두 내보낸다. 파일 이름에 `A-LAN`, `B-LTE`처럼 붙인다.

### 3.11 (선택) QoS 표시 확인 — Wireshark (P1-3)

1. PC B에 Wireshark를 설치하고 사용 중인 어댑터로 캡처를 시작한다. 필터는 `udp && ip.src == <A_IP>`.
2. 합주 중 패킷 하나를 골라 **Internet Protocol → Differentiated Services Field**를 본다. `DSCP: EF (46)`이면 표시가 유지된 것이다. `CS0`(0)이면 지워졌거나 표시되지 않은 것이다.
3. PC A의 **QoS 줄**(3.2절, 예: `QoS Voice 1/1(관리자 권한 필요)`)과 함께 적는다. 일반 권한 실행은 `Voice`가 정상이고 이때 실제 DS 값은 OS 정책에 따른다. 관리자 권한 PowerShell에서 앱을 실행하면 `ef`가 될 수 있다(선택 비교).
4. 송신 PC(A) 자신의 캡처에는 표시가 안 보인다는 보고가 있다. 반드시 **받는 PC(B)** 에서 본다.

### 3.12 (선택) 관람 웹

웹은 관람(청취) 전용이다. 운영 웹(`indigomuse.art`)은 운영 서버에 붙으므로 이 세션의 방(로컬 서버)은 보이지 않는다. 그래서 PC B에서 앱과 함께 떠 있는 개발 웹(Vite, `https://localhost:5173`)을 브라우저로 연다. 아래는 코드 기준 절차이고, 2대 세션에서 아직 해 본 적이 없다 — 막히면 그 단계와 화면 문구를 적는다.

1. PC B의 Chrome/Edge에서 `https://localhost:5173/settings/audio`를 연다. `client\certs`가 없으면 자체 서명 인증서 경고가 뜬다 → 고급 → 계속.
2. 페이지의 "데스크톱 앱 전용 기능" 안내 아래 **개발 서버 (개발 실행 전용)** 칸에 `<A_IP>:8080`을 넣고 **저장 후 새로고침**. 이 값은 브라우저마다 따로 저장된다(앱 창에 넣은 값과 별개).
3. **로그인하지 않은 상태**로(또는 두 PC와 다른 셋째 계정으로) **합주실** → 방 코드 → **입장**. 두 PC의 계정으로 로그인하면 같은 계정의 연주 쪽 연결이 끊긴다(7절 표 맨 아래).
4. 왼쪽 패널에 "🖥️ 연주는 데스크톱 앱에서", 가운데에 "👀 관람 모드"가 보인다. 가운데 개인 믹서가 "합주 방송에 연결 중..."에서 방송 채널로 바뀌고 두 PC의 합주가 들리는지 본다.
5. 연주하는 PC 중 한 대의 내 행에 **📡 방송** 배지(마우스를 올리면 "관람자 1명에게 믹스 송출 중")가 붙는지 본다.
6. 로그인하지 않은 관람자는 채팅을 보낼 수 없다(P2-14c). 오른쪽 채팅 아래에 입력창 대신 "로그인하면 채팅할 수 있어요"와 **로그인** 링크가 보이는지 확인한다(입력창이 보이면 그 사실을 적는다). 두 PC가 보낸 채팅은 읽을 수 있어야 한다.

같은 PC B에서 앱(연주)과 브라우저(관람)를 함께 켜면 같은 헤드폰으로 합주가 두 번 겹쳐 들린다. 관람 웹 소리를 확인하는 동안에는 앱의 개인 믹서 **마스터**를 음소거하고, 끝나면 되돌린다.

## 4. 2부 — 다른 네트워크 (P1-8, P1-4d, P1-4c)

PC B만 다른 네트워크로 옮긴다. PC B를 휴대폰 **LTE 핫스팟**에 연결하는 것이 가장 쉽다. PC B가 다른 네트워크에 있으면 2.3절의 `A_IP`(LAN 주소)로는 서버에 닿지 않는다. 그래서 PC A의 서버를 인터넷에 열어야 한다.

**개발 서버** 칸은 보안상 localhost와 사설 IP만 받는다(공인 IP 입력은 거부). 그래서 2부에서만 PC B의 Windows 포트 프록시로 **PC B의 `localhost:8080`을 A_PUB로 넘기고**, 개발 서버 칸은 **기본값**(`localhost:8080`)으로 둔다. PC B는 2.3절대로 `npm run tauri:dev`로 실행해 8080 포트가 비어 있어야 한다.

### 4.1 PC A 서버를 인터넷에 열기 (테스트 동안만)

1. PC A의 공인 IP를 확인한다: 브라우저에서 "내 IP"를 검색하거나 PowerShell에서 `curl.exe https://ifconfig.me`. 이 값이 **A_PUB**이다.
2. 공유기 관리 화면(ipTIME이면 보통 `192.168.0.1`)의 **포트 포워드**에 다음 규칙을 추가한다:
   - TCP **8080** → A_IP:8080 (시그널링 서버)
   - (4.2절 릴레이를 쓸 때) UDP **5000** → A_IP:5000
3. PC B에서 **관리자 권한** PowerShell(시작 → PowerShell 마우스 오른쪽 → 관리자로 실행)을 열고 포트 프록시를 추가한다:
   ```powershell
   netsh interface portproxy add v4tov4 listenaddress=127.0.0.1 listenport=8080 connectaddress=<A_PUB> connectport=8080
   ```
4. PC B 브라우저에서 `http://localhost:8080/health`를 열어 응답을 확인한다.
5. PC B 앱의 🎛️ 오디오 설정 창 맨 아래(2.3절 6번) **개발 서버** 칸에서 **기본값**을 누른다. `지금 연결: http://localhost:8080`이 되면 된다.

⚠️ 개발 서버(운영 DB의 서비스 키를 가진 서버)가 테스트하는 동안 인터넷에 열린다. 모든 요청은 로그인 토큰으로 인증되지만, **테스트가 끝나면 바로 포트 포워드 규칙을 지운다**.

### 4.2 (선택) 로컬 릴레이 켜기

릴레이가 없으면 직접 연결(홀펀칭)이 실패했을 때 **연결 실패**("직접 연결 불가 — 네트워크(대칭형 NAT) 문제, 릴레이 서버 없음")가 된다. 릴레이 폴백까지 확인하려면 PC A에서 릴레이를 띄운다.

1. PC A에서 앱과 서버(2.2절 창)를 `Ctrl+C`로 끈다.
2. 새 PowerShell 창에서 비밀값을 만들고 릴레이를 실행한다(릴레이 설정 값의 원본은 [relay/README.md](../relay/README.md) — `RELAY_SECRET`은 32바이트 이상, UDP 기본 `0.0.0.0:5000`). 비밀값은 어디에도 저장하지 않는다.
   ```powershell
   $secret = -join ((1..32) | ForEach-Object { '{0:x2}' -f (Get-Random -Maximum 256) })
   $secret | Set-Clipboard          # 다음 창에 붙여 넣기 위해 클립보드로
   cd C:\dev\devdev\band-tauri\relay
   $env:RELAY_SECRET = $secret
   cargo run --release
   ```
   `[relay]` 로그가 뜨고 UDP 5000을 연다. `relay.exe` 방화벽 경고는 개인·공용 모두 허용한다.
3. 2.2절 창에서 같은 비밀값과 공인 주소를 넣고 다시 실행한다:
   ```powershell
   cd C:\dev\devdev\band-tauri
   $env:RELAY_SECRET = Get-Clipboard
   $env:RELAY_ADDR = '<A_PUB>:5000'
   npm run dev:tauri
   ```
   서버를 다시 띄웠으므로 `[MAINT] … 건너뜀` 줄을 다시 확인한다(0절 ⚠️).
4. 한계: PC A 자신도 `A_PUB:5000`으로 릴레이에 붙는다. 공유기가 **NAT 루프백(헤어핀)** 을 지원해야 한다(ipTIME 등 대부분 지원). 지원하지 않으면 PC A의 릴레이 상태가 `unreachable`이 되고 릴레이 경로가 성립하지 않는다. 릴레이 상태는 아직 화면에 없으니 개발자 도구 명령(3.2절)의 `relay.state`로 확인한다(`bound` = 등록됨).

### 4.3 다른 네트워크에서 연결

1. PC B를 LTE 핫스팟에 연결하고(4.1절 3~5번을 이 상태에서 확인), 앱이 꺼졌으면 2.3절 4번으로 다시 실행해 방에 다시 들어간다.
2. 두 PC 모두 **🎤 연주 참여하기**.
3. 상대 채널의 경로를 본다:
   - **인터넷**: 홀펀칭으로 직접 연결됐다(콘형 NAT).
   - **릴레이** + "서버 경유 — 지연 증가": 직접 연결이 안 돼 릴레이로 폴백했다(대칭형 NAT, LTE에서 흔함).
   - **연결 실패**: 문구를 그대로 적는다(7절 "연결 안 됨").
4. 3.2절처럼 RTT, 버퍼, 목표, 은닉, 손실, **첫 소리**를 1분 동안 보고 기록한다(첫 소리는 PC B가 **👀 관람자로 전환** → **🎤 연주 참여하기**를 3번 반복해 각각 적는다, P1-20). 에코 측정(3.4절)을 3번 해서 경로(`lan` / `public` / `relay`)와 함께 적는다.
5. **10분 연주**(P1-4d): 경로를 유지한 채 10분 동안 연주하며, 끊김이 몇 번 들렸는지 귀로 센다. 끝나고 은닉 %와 재연결 횟수를 적는다.
6. 릴레이 경로라면 `relay.rttMs`(엔진 ↔ 릴레이)와 `peers[].rttMs`(릴레이를 거친 종단 간)를 함께 적는다.
7. 3.8절 일시 단절(핫스팟 Wi-Fi 끄기 5초)을 한 번 더 한다. 릴레이 경로에서 직접 경로로 승격되거나 반대로 바뀌는 순간 소리가 끊기지 않는지 본다.
8. (선택, P1-4d "시계 오차 PC") PC B의 Windows 시계를 **설정 → 시간 및 언어 → 자동으로 시간 설정 끄기 → 수동으로 5분 앞당김**으로 바꾸고 다시 입장한다. 릴레이 토큰은 받은 시각 기준으로 판단하므로 연결이 유지되어야 한다. 끝나면 자동 시간 설정을 다시 켠다.

### 4.4 Opus 자동 전환 확인 지표 (P1-4c)

자동 전환 조건은 "PCM16 설정 + 릴레이 경로 피어의 예상 송신량이 2 Mbps의 90% 이상"이다. PC 2대로는 릴레이 피어가 1명뿐이다. PCM16 모노 2.5ms는 약 0.9 Mbps(45%)이고 스테레오 2.5ms도 약 1.67 Mbps(84%)라서 **2대로는 전환이 일어나지 않는다**. 3대 이상(같은 PC에 릴레이 피어 2명)이 있어야 켜진다.

이번 세션에서는 **전환되지 않는 것(대조군)** 만 확인한다:
1. 두 PC를 **초저지연**(PCM16) 프리셋으로 바꾸고 엔진을 다시 켠다. 경로가 **릴레이**일 때만 의미가 있다.
2. 개발자 도구 명령에서 `relay.autoOpus: false`, `relay.overBudget: false`, `peers[].txCodec: "pcm16"`, `txCodecAuto: false`, `relay.txKbps`(약 900 안팎)를 적는다.
3. 상대 채널에 "대역 절약을 위해 Opus로 자동 전환"이나 "릴레이 대역 초과"가 뜨지 않아야 한다.

3대가 있을 때 확인할 지표(다음 세션용): 릴레이 경로 피어 2명 이상 + PCM16이면 상대 채널에 **"서버 경유 — 대역 절약을 위해 Opus로 자동 전환"** 이 뜬다. `relay.autoOpus: true`, `peers[].txCodec: "opus"`, `txCodecAuto: true`가 된다. 로그에는 `릴레이 대역: 릴레이 피어 N명에게 Opus로 전환(…)`이 남는다. 전환 순간 소리가 툭 끊기지 않는지 청취한다.

### 4.5 2부 정리

1. 두 PC에서 진단 내보내기(3.10절).
2. PC A 공유기에서 포트 포워드 규칙(TCP 8080, UDP 5000)을 **삭제**한다.
3. PC B 포트 프록시를 삭제한다(관리자 PowerShell):
   ```powershell
   netsh interface portproxy delete v4tov4 listenaddress=127.0.0.1 listenport=8080
   ```
   PC B의 **개발 서버** 칸은 **기본값** 그대로 두고, 두 PC의 앱·개발 서버를 끈다(2.3절 끝).
4. 릴레이 창을 `Ctrl+C`로 끈다. 시계를 바꿨다면 자동 시간 설정을 다시 켠다.
5. 방장이 합주실의 **ℹ️ 정보** → **🗑️ 합주실 삭제**로 `[TEST]` 방을 지운다.
6. 3.12절을 했다면 관람 웹을 연 브라우저에서 `https://localhost:5173/settings/audio`의 개발 서버 칸을 **기본값**으로 되돌린다.

## 7. 문제가 생기면

### 연결 안 됨

| 증상 | 확인 순서 |
|---|---|
| 로그인은 되는데 방에 들어가면 계속 연결 중이거나 채팅·연주자 목록이 안 뜸 | ① PC A 터미널에 서버가 떠 있는가 ② 🎛️ 오디오 설정 창의 **개발 서버** 칸 `지금 연결:` 주소가 맞는가(PC A = `http://localhost:8080`, PC B = `http://<A_IP>:8080`, 2부 PC B = `http://localhost:8080` + 포트 프록시) ③ PC B 브라우저에서 `http://<A_IP>:8080/health` 응답 ④ PC A `node.exe` 방화벽 허용 ⑤ 실행한 창에 예전 `$env:VITE_SIGNALING_URL`/`$env:VITE_API_URL`이 남아 있지 않은가(새 창에서 다시 실행) |
| **개발 서버** 칸이 페이지에 없음 | `VITE_SIGNALING_URL`·`VITE_API_URL`을 둘 다 직접 지정했거나(새 창에서 다시 실행) 개발 실행이 아니다(설치본·`vite build`). |
| `개발 서버 프록시: http://… 연결 실패 (…)` | 대상 서버에 닿지 않는다. 대상 주소·포트, PC A 서버와 방화벽을 확인한다 |
| PC B에서 `/health`가 안 열림 | ① A_IP가 맞는가(PC A `ipconfig`) ② PC A 방화벽 ③ 2부라면 `netsh interface portproxy show all`로 규칙 확인, 공유기 포트 포워드와 A_PUB |
| PC B에서 앱 실행 직후 꺼짐 | `npm run dev:tauri`는 서버와 앱을 함께 띄워, 서버가 시작에 실패하면(`server\.env` 없음, 2부 포트 프록시와 8080 충돌 `EADDRINUSE :8080`) 앱까지 같이 끈다. PC B는 `npm run tauri:dev`로 실행한다 |
| 8080이 아닌 포트로 서버를 띄웠는데 연결 안 됨 | 다른 PC의 개발 서버는 허용된 포트로만 넘긴다. PC B 실행 창에 `$env:BAND_DEV_PROXY_PORTS = '<포트>'`를 넣고 다시 실행한다(2.2절) |
| 상대 배지가 계속 **연결 중** → **연결 실패** | ① 두 PC의 `band.exe` 방화벽 허용(공용 포함). 거부했다면 **Windows 보안 → 방화벽 및 네트워크 보호 → 방화벽에서 앱 허용**에서 band 항목을 체크 ② 같은 LAN인데 실패하면 공유기 "AP 격리/게스트 Wi-Fi" 해제 ③ 2부라면 4.2절 릴레이 |
| **연결 실패** 옆 문구 | "직접 연결 불가 — 네트워크(대칭형 NAT) 문제, 릴레이 서버 없음" = 릴레이를 켜지 않았다(4.2절). "연결 불가 — 직접 연결 실패, 릴레이 서버에 닿지 않음" = 릴레이 등록이 안 됐다(UDP 5000 포워드, 헤어핀, 릴레이 창). "연결 불가 — 직접 연결과 릴레이 모두 실패 (상대 네트워크 확인)" = 내 쪽 릴레이 등록은 됐는데 상대와 이어지지 않는다(상대 PC 쪽 확인). "연결 불가 — 릴레이 인증 만료 (새 인증 요청 중)", "연결 불가 — 릴레이 서버가 연결을 거절했습니다"(두 창의 `RELAY_SECRET`이 같은지), "연결 불가 — 직접 연결 실패, 릴레이 설정 실패(…)"(괄호 안 사유)는 그대로 적는다 |
| **연주 참여하기**가 승인 대기에서 멈춤 | 방장이 연주자 패널의 **연주 참여 요청** → **✓ 승인**을 눌렀는가. "방장이 지금 접속해 있지 않습니다. 방장이 들어오면 요청이 전달됩니다."면 PC A가 방에 있는지 확인 |
| 엔진 시작 실패 | ✅ 승인됨 아래 "엔진을 자동으로 시작하지 못했습니다. 설정을 확인한 뒤 다시 시도하세요."가 뜨면 🎛️에서 드라이버를 **WASAPI 공유**로 바꾸고 **🎤 연주 시작하기**. 다른 앱(DAW, 브라우저 통화)이 장치를 독점하고 있으면 끈다 |
| 위쪽에 "다른 창이나 기기에서 이 합주실에 들어와 여기 연결은 종료됐습니다" | 같은 계정으로 다른 창·기기(관람 웹 포함)에서 같은 방에 들어왔다. 두 PC·관람 웹이 서로 다른 계정(또는 관람 웹은 로그인 없이)인지 확인 |

### 소리가 안 남

1. 🎛️ **테스트 모니터 → 테스트 시작**으로 내 입력·출력이 되는지 먼저 본다(합주 중이면 관람자로 전환한 뒤).
2. 개인 믹서의 **마스터** 볼륨과 🔇, 상대 채널의 🔇·볼륨.
3. 내 행의 마이크 버튼이 **마이크 끄기** 상태가 아닌지(상대에게 무음).
4. 상대 채널의 레벨 미터가 움직이는데 안 들리면 출력 장치 선택. 레벨이 안 움직이면 상대 쪽 입력 문제.
5. 클릭만 안 들리면 메트로놈 🔔/🔇과 클릭 볼륨, 마스터 볼륨(클릭도 마스터를 탄다).
6. 하드웨어 루프백이 0~1ms이거나 "신호 미검출"이면 [MEASURE.md](MEASURE.md) 7절.

### 끊김·지직거림

1. **xrun**이 늘어나면: 내 PC 쪽 문제다. 장치 버퍼를 128 → 256으로 올리거나 WASAPI 독점으로 바꾼다. 무거운 앱을 끈다. 노트북은 전원을 연결하고 전원 모드를 "최고 성능"으로 둔다.
2. **손실 %** 가 오르면: 네트워크 문제다. 유선으로 바꾼다. 같은 회선에서 동영상 스트리밍·다운로드를 멈춘다.
3. **은닉 %** 가 1.5%를 넘는데 손실이 0이면: 지터 문제다. 🎛️ 지터 버퍼 슬라이더를 **안정** 쪽으로 옮긴다(합주 중 바로 적용). 이때 버퍼 지연 변화도 적는다.
4. 증상이 있었던 시각을 메모하고 **바로 진단 내보내기**를 한다. 타임라인에서 그 시각을 찾을 수 있다.

**zip을 받은 뒤(코디네이터) — 결과표 뽑기**: 받은 진단 zip들을 한 폴더에 두고 `cd client/src-tauri`(PowerShell·bash 모두) → `cargo run -p band-engine --example diag_report -- <zip> [<zip> ...]`. zip마다 세션 요약(앱 버전·시각·길이·백엔드·드라이버·프리셋·프레임·코어 배치·xrun 증가 시점), 피어별 표(bufferMs 중앙/p95/최대, 은닉 %(방식별), 손실 %, 손실 모양, 경로, RTT, 연결·첫 소리 ms), 연결 기록, GOAL 1·2절 판정표를 내고, 끝에 모든 zip을 합친 연결 성공률 집계(경로별 시도·성공·실패·중단·중앙 소요 ms)와 3절 판정을 Markdown으로 낸다(`--json`이면 같은 값을 JSON으로). 판정은 충족 / 미달 / 판정 불가(데이터 없음·세션이 기준보다 짧음·측정 구간이 GOAL 정의와 다름 — 비고에 이유)다. 충족은 근거가 완전할 때만 낸다: 은닉 %는 재생 프레임(`produced`) 분모, 3-3 첫 소리는 엔진 피어 추가부터라 충족을 내지 않고(3초 초과·소리 못 받음만 미달), 3-2 시도 수는 기록 기준이라 한 합주의 양쪽 zip을 함께 주면 98% 문턱은 겹치는 세션의 큰 쪽만 센다. 청감과 회선 종류(유선/Wi-Fi, NAT)는 진단에 없으니 이 기록표 값으로 채운다. GOAL 1-4(±3ms 1분)·2-1(은닉 %)은 이 도구와 같은 PR(#246)부터 타임라인에 기록되는 `targetMs`·`produced`가 필요해, 그 전 빌드의 zip은 판정 불가로 나온다. 기준값은 `crates/band-engine/src/diag/report/mod.rs`의 `goal` 한 곳(GOAL.md 절 번호 주석).
