# GOAL 2~4절 구현 점검 (2026-11-12)

기준: `origin/develop` ce1628c, [GOAL.md](../GOAL.md) 2절(안정성)·3절(연결성)·4절(사용성).
방법: 코드를 열어 항목마다 구현 위치와 테스트를 찾았다. **이 점검에서 테스트·하네스를 다시 돌리지는 않았다.** 수치는 코드 주석·설계 문서·백로그에 기록된 값을 옮긴 것이고 그렇게 표시했다. 실장비·실네트워크는 확인하지 않았다.

"있음"은 "코드와 자동 테스트가 있다"는 뜻이다. GOAL 수치가 실제 장비·회선에서 나온다는 뜻이 아니다. 그 구분은 마지막 절에 따로 적었다.

가장 무거운 발견은 **WS 재연결(2-6)** 이다. 서버 유예 30초와 엔진 유지 35초는 맞춰져 있는데, 그 사이를 잇는 클라이언트 재시도가 세 번(각 2초 뒤)뿐이고, 서버가 끊김을 아직 모르는 동안에는 재개 자체가 되지 않는다. 둘 다 자동 테스트가 없다.

### 2-6 상세 — WS 재연결의 빈 곳

**(a) 클라이언트 재시도 예산이 30초가 아니다.** `features/room/state/useSignaling.ts`: `MAX_RECONNECT = 3`, `RECONNECT_DELAY_MS = 2000`. 닫히면 2초 뒤 다시 연결하고, **열리는 데 성공해야** 횟수가 0으로 돌아간다. 망이 내려가 있어 연결 시도가 곧바로 실패하면 세 번이 약 6초 안에 소진되고 그 뒤로는 시도하지 않는다. 10초짜리 단절이면 서버는 아직 20초를 기다리고 엔진도 25초 더 살아 있는데, 다시 붙으려는 쪽이 없다. 35초 뒤 `performSession`이 "시그널링 서버 연결이 끊겨 연주를 중단했습니다."로 정지한다. (연결 시도가 OS 타임아웃까지 매달리는 경우에는 더 오래 버티지만 그건 우연이다.) `useSignaling`에는 단위 테스트가 없다.

**(b) 서버가 끊김을 모르는 동안에는 재개가 안 된다.** `handleAuth`는 `suspended.get(resumeClientId)`가 있을 때만 재개한다. `suspended`에는 서버가 소켓 `close`를 **받은 뒤에** 들어간다. 랜선을 뽑거나 와이파이가 바뀌면 서버는 FIN을 못 받고, 하트비트(30초 주기 — 감지까지 30~60초)가 지나야 닫힘을 안다. 그 전에 클라이언트가 새 소켓으로 `resumeClientId`를 보내면 재개되지 않고 새 clientId를 받는다 → `performSession.welcome`이 "이전 엔진 정지 후 새 id로 재시작"한다 → **오디오가 끊긴다.** 이어지는 `join`이 옛 연결을 중복으로 정리하므로 다른 연주자에게는 `participant-left` 뒤 `participant-joined`가 간다. 서버 테스트는 `close()`를 깨끗이 부른 경우만 본다.

**(c) 클라이언트는 죽은 소켓을 스스로 알아채지 못한다.** 서버의 `ws.ping()`에 브라우저가 자동으로 pong을 보낼 뿐, 클라이언트 쪽에는 "일정 시간 아무것도 안 옴" 검사가 없다. 한쪽만 죽은 소켓이면 `onclose`가 오래 안 와서 (a)의 재시도조차 시작되지 않는다. 그동안 엔진·UDP는 계속 돌아 소리는 이어지지만 시그널링이 멎어 있다(새 연주자 descriptor, 릴레이 토큰 갱신 — 토큰 수명 120초).

**(d) 서버 재시작·배포.** 세션 상태가 전부 메모리라 프로세스가 다시 뜨면 `suspended`가 없다. `main` 배포마다 접속 중인 연주자 전원이 새 clientId로 엔진을 재시작한다. 장시간 하네스 머리말도 "세션 재개 실패(새 clientId)는 엔진 재시작이라 '끊김 없음' 범위 밖"이라고 적는다. 자세한 것은 [server-architecture.md](../server-architecture.md) 2.4절.

## 점검의 한계

- 테스트를 실행하지 않았다. "테스트가 있다"는 "그 이름의 테스트가 코드에 있다"이고 "지금 녹색이다"는 CI가 답한다.
- "찾지 못함"이라고 쓴 것은 검색(`grep`)으로 못 찾았다는 뜻이다. 다른 이름으로 있을 수 있다.
- 2-6 (a)·(b)는 코드를 읽어 추론한 동작이고 재현 테스트로 확인하지 않았다. P1-15·P1-16의 첫 단계가 그 재현 테스트다(먼저 실패하는 테스트를 쓰고 고친다).
- 4-13 ①은 주소 문자열이 다르다는 사실까지만 확인했다. 실제로 업데이트가 깨지는지는 모른다.
